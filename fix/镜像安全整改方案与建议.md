# 镜像安全整改方案与建议(超危/高危)— py3.12 迁移版

> 配套文档:`fix/镜像安全评估分析报告.md`(麒麟版归因,保留作旧链底账)
> 目标:**py3.12 新镜像送评时超危/高危清零**(豁免项除外)。
>
> **2026-09-07 行内基座盘点结论(数据:fix/logs.txt)**:行内基座 rpm 系统层基本打满补丁(glibc p12 / libxml2 p16 / krb5-libs 1.18.2-23 / curl-47 / pam p06 / libssh-16 / libarchive-14),**旧链的超危/高危 rpm 在行内基座上要么是补丁版、要么不存在**(无 perl、无 unbound-libs),仅剩 py3.7 的 pip/setuptools 2 条高危(即 kylin12.xlsx 报告)。py3.12.10 已就位(`/opt/python3.12.10-x86_64-bin`,pip 25.0.1 + venv OK + PATH 置顶,非 rpm 安装),无 conda。**yum 实测可用(2026-09-07 二次测试)**:yum makecache 成功(base/updates,网络全通),krb5-workstation 安装成功——**离线打包方案作废**,材料全部行内 yum 装;py3.7 的 2 条高危可走 yum 删 dnf 链。**但发现降级风险**:安装 krb5-workstation 时 yum 把基座自带 krb5-libs 1.18.2-**23.ky10** 降级为 **1.18.2-17.ky10**(行内 updates 源版本滞后于基座构建时间)——需确认 17.ky10 是否被评估平台认可(平台推荐为 17.a.ky10),并对其他"基座比源新"的包(glibc p12/libxml2 p16/curl-47 等)加 `--exclude` 防降级。一次"yum 装材料"的报错(旧容器 /usr/bin/python 缺失)已随新容器消失,解释器问题不复发。
>
> 决策记录(2026-09-04):
> 1. 行内要求**必须使用 py3.12**,py3.9 不再允许 → 现行 py3.9 麒麟链(kylin-20260730-v6)整改**跳过**,其 8 超危/45 高危作为迁移期已知风险,迁移后自然消失;
> 2. 行内 py12 基座**不能带出行内**、**无 yum 源** → 新镜像必须"行外备料、行内组装";
> 3. 行内基座自带 py3.12 → 新镜像**不再需要 Miniconda/conda**(现行链用 conda 只是因为老麒麟没有可用 Python),整链更简单。

## 1. 方案总览:先搓基座,再跑应用,两条轨道并行

按"**先搓基座(纯 rpm 层)→ 基座单独送评定版 → 再把项目跑上 py3.12(应用层)→ 合流**"的顺序推进:

| 轨道 | 内容 | 地点 | 周期 |
|---|---|---|---|
| **A. 基座先行** | A1 行外备 rpm 材料(§4)→ A2 行内搓"应用基座"(行内 py12 基座 + 必要 rpm,**无 gcc 编译链**——pip 依赖全用预编译 wheel)→ **基座单独送评定版**(§5) | 行外备料 + 行内组装 | 3~5 天 |
| **B. 项目适配 py3.12**(并行) | requirements.txt 升级 + 风险包实测编译 + 代码适配 + 行外验证环境跑通(§3) | 行外 | 1~2 周 |
| **合流** | FROM 应用基座 → pip --no-index 装 wheels → COPY myapp → 最终送评 → 灰度(§5/§6) | 行内 | 1 周 |

为什么基座先行:

1. 基座工作纯机械、不依赖应用改造的决策,先把"材料能否过行内安全扫描、行内能否装 rpm"这些不确定性打掉;
2. 基座单独送评一次(门禁:超危/高危清零),问题面小、好排查,通过后定版;后面应用层的问题就不会和 rpm 层混在一起;
3. 现行链的 pip 修复目标(FAB 4.8.1/Werkzeug 3.1.6 等)全部并入轨道 B 的升级清单,一次改动两处受益(安全销项 + py3.12 兼容)。若行内整改期限提前、需要旧链兜底,旧链 rpm 补丁目标版本见 `cube-kylin.xlsx` 评估平台推荐版本列。

**前端镜像同步处理**:前端分两段——(1) **行外构建**:`npm install && npm run build`(需要 node/npm,但只在行外构建机上,产出静态产物);(2) **行内组装**:`FROM 行内基座 → 装 nginx(+依赖)→ COPY 静态产物 → nginx 配置`(静态文件要有 web 服务器;nginx 走 yum 实测或离线 rpm,见 §4 ⚠)。建议前端**单独搓一个"前端基座"**(行内基座 + nginx 即可),不要复用后端应用基座(gcc/krb5/sasl 等前端用不到,徒增评估面)。同样走"备料 → 行内组装 → 送评"门禁(前端镜像此前从未送评,nginx 版本是主要风险点);node/npm 不进镜像。

### 4.1b py3.7 残留(pip 20.2.2 / setuptools 44.1.1,基座仅有的 2 条高危)处置

py3.7 是 rpm 版 `python3-3.7.9` **且被 dnf 依赖**(python3-dnf/python3-rpm/python3-hawkey/python3-libdnf/python3-libcomps/python3-gpgme 均基于 py3.7),不能直接删:

| 方案 | 做法 | 评估 | 前提 |
|---|---|---|---|
| ① 删 dnf 链(推荐) | 修复 `/usr/bin/python3` 缺失后,行内 `yum remove dnf yum python3-dnf python3-rpm python3-hawkey python3-libdnf python3-libcomps python3-gpgme python3`(镜像不需要包管理) | 2 条高危整组消失,最干净;可能连带少量无关包,需确认 | **yum 修复且网络可达** |
| ② py3.7 内升级 | `python3.7 -m pip install -U pip setuptools` | **修不干净**:CVE-2024-6345 修复版 setuptools 70+ 要求 py≥3.8,py3.7 最高 68 仍含漏洞 → 升级后仍需评估豁免 | 无需条件 |
| ③ 基座团队处理 | 请基座团队把 dnf 链换 py3.12 / 镜像内不再带 dnf(并修复 /usr/bin/python3 缺失) | 需沟通协调,但一劳永逸 | 基座团队配合 |

## 5. 轨道 A2 + 合流:行内搓基座、组装与送评

**A2 行内搓"应用基座"(先做,独立送评定版)**:

```
FROM 行内 py12 基座
  → yum install -y krb5-workstation jq unzip fontconfig wqy-microhei-fonts kubectl二进制 --exclude=<基座比源新的包>(§4 ⚠防降级)
  → py3.7 处置(§4.1b):yum remove dnf 链(推荐,方案①)——先跑 yum check-update 确认无其他降级
  → 打 tag:应用基座 v1
```

→ **基座单独送评一次**:门禁超危/高危清零(豁免项除外)。此时镜像里还没有 pip 应用依赖,问题面小、好排查;通过后基座定版。

**合流(基座定版之后)**:

```
FROM 应用基座 v1
  → python3.12 -m venv 建应用环境
  → pip install --no-index --find-links ./wheels
  → COPY myapp
```

→ 最终送评:超危/高危清零(豁免项除外)→ 进入 §6 灰度。

- gcc/gcc-c++/make 等编译工具只用于构建期;pip 全部用预编译 wheel 时可完全不装(风险包 sasl/gmssl 已在行外编译成 wheel,但注意其依赖的 krb5/cyrus-sasl **运行库**必须随 rpm 材料带入行内);
- 若基座团队愿意定制(§2-1),A2 只剩"装 wheels + COPY myapp",最省事。

**前端镜像组装(与后端合流并行)**:

```
FROM 行内基座(或单独的前端基座)
  → rpm -ivh nginx + 依赖
  → COPY 行外构建好的静态产物 + nginx 配置
```

→ 送评(前端镜像从未评过,重点看 nginx 版本与 GPL 类许可)。
