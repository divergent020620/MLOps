## 步骤 4 安装必需 rpm(防降级 exclude)

### 4.0 krb5-libs 保全方案(先做,三选一,推荐 A)

**方案 A(推荐,2026-09-07 已完成)downloadonly 取 kinit + 补库,不降级 krb5-libs:**
```bash
# ① 补 cpio(基座精简版没有;新装无降级风险)
yum install -y cpio --exclude=$EXCL

# ② 下载 krb5-workstation 依赖(仅下载不安装)
#   ★ dnf 4.2 的 install 不支持 --downloaddir,包默认进缓存
#   ★ 缓存会在"下一次成功 yum 事务"被清空(实测:装 cpio 即清)!
#   ★ 下载后必须立刻转移,中间不做任何其他 yum 操作
yum install -y --downloadonly krb5-workstation
find /var/cache/dnf -name "*.rpm" -exec cp {} /root/krb5dl/ \; -print
ls -l /root/krb5dl      # 应有 7 个 rpm(krb5/krb5-client/krb5-libs/e2fsprogs/fuse/fuse-common/which)

# ③ 解包:只提取 kinit,不安装任何包、不降级
cd /root/krb5dl && for f in *.rpm; do rpm2cpio "$f" | cpio -idm; done
find usr -name "kinit*"                          # usr/bin/kinit
cp usr/bin/kinit /usr/bin/kinit && chmod +x /usr/bin/kinit

# ④ 补 kadm5srv 库(kinit 链接需要;库文件就在 krb5 主包解包目录里)
cp -d /root/krb5dl/usr/lib64/libkadm5srv_mit.so.12* /usr/lib64/
ldconfig 2>/dev/null || true

# ⑤ 验证(kinit -V 应打印 1.18.2-17...,库加载通过即完成)
kinit -V
```
→ krb5-libs 保持 1.18.2-23 不动,**零降级**;rpmdb 无任何变化。
注:krb5.conf **不放占位**——部署阶段 COPY 行内真实配置(用户行内已有);kinit 真实验证在部署后用行内 keytab 进行。
兜底(若缓存被清/插件可用):`dnf download krb5-workstation --resolve --destdir /root/krb5dl`(需 dnf-plugins-core,报 Unknown command 则走上面流程)。

**方案 B 要 rpm 包装回(用户思路):**
```bash
# 1. 先找缓存(大概率没有;有就直接跳到 3)
find / -name "krb5-libs-1.18.2-23*.rpm" 2>/dev/null
# 2. 没有 → 向基座团队要 krb5-libs-1.18.2-23.ky10.x86_64.rpm(构建基座的源/缓存必有)
# 3. 装完 krb5-workstation 后:
#    rpm -Uvh krb5-libs-1.18.2-23.ky10.x86_64.rpm
```

**方案 C 兜底**:正常装(接受临时降级为 17),送评看结果,平台报 CVE 再豁免或补装回。

## 步骤 7 (可选)jupyter 编译链 / 前端 nginx

**7a. jupyter 镜像 ⚠ 实测(2026-09-07):编译链与基座补丁水平结构性冲突,不装**

`gcc gcc-c++ make ... --exclude=$EXCL` 失败(实测报错),根因:**行内源比基座旧**——源里编译链元组配套的是旧版
(openssl-libs p29 < 基座 p34 / libstdc++ p01 < 基座 p03 / glibc p02~p05 < 基座 p12 / bzip2 obsoletes),而 exclude 挡着基座新版:
- 装编译链 = 必须降级 glibc p12→p05(旧链超危 CVE-2025-4802 版本!)、openssl p34→p29、libstdc++ p03→p01 → 送评必炸 ❌

**结论:jupyter 也走零编译链策略(与前后端统一),且实测确认不需要**:
- **gcc 的唯一用途 = notebook 内用户 pip install 源码包时现场编译**;现行 domestic-jupyter 构建流程实际只用 node(pip 全是预编译包),gcc 从未被使用;
- 我们场景:**jupyter 用户不能自行 pip install** → gcc 完全无用,不装无任何影响;
- 若将来开放用户装包:走行内 pypi 镜像(manylinux wheel 全覆盖)+ 少数源码包(sasl/gmssl 等)由行外预编译 wheel 分发——仍不需要 gcc;
- 若行内验收标准硬性要求 jupyter 镜像含编译链(现实基本无此类标准)→ 才需基座团队用其构建源(元组配套新版)提供,不在行内组装机上硬装。

**7b. 前端镜像**是独立镜像,建议另起容器(步骤 8 的注释流程,基座+nginx,不再装后端依赖):
```bash
docker run -d --name fe-build01 <同一基座:tag> bash -c "sleep 3600"
docker exec -i fe-build01 bash -c 'ln -sf /usr/bin/python3.7 /usr/bin/python; yum install -y nginx --exclude=$EXCL; nginx -v'
# 之后:docker cp 行外构建好的 dist → fe-build01:/usr/share/nginx/html
#      docker stop fe-build01 && docker commit fe-build01 <新前端tag> && docker save
```
