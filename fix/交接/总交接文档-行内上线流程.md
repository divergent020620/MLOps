# 总交接文档:行内 M1 后端镜像(py3.12)上线全流程

> 对象:组装+切换同事(有行内 docker / kubectl 权限)
> 前置:该文档配套文件已在交接包内(见 §1 材料清单)
> 原则:**照抄命令、按顺序执行、异常截图交回,不擅自改版本/配置**

---

## 0. 你只需要记住的一句话

**构建一个新后端镜像 → 推行内仓库 → 更新 ConfigMap + 换 4 个 deployment 的 tag → 观察 10 分钟 → 达标交回。**

旧镜像保留(kylin-20260730-v6),随时可回退,风险可控。

## 3. 构建镜像(方式 B,Dockerfile,推荐)

```bash
# 0) 前置: 在行内构建机执行(建议 k8s-master1/2/3 任一台, 有 docker+harbor 权限), 并先登录 harbor
docker login 10.240.125.39 -u <harbor账号> -p <harbor密码>

# 1) Dockerfile 已内置行内地址(10.240.125.39/cube-studio), 无需修改
# 2) 在 cube312-build/ 内执行(context=它, Dockerfile 就在当前目录):
cd cube312-build
docker build -t 10.240.125.39/cube-studio/kubeflow-dashboard:app-p312-v1 \
  -f Dockerfile.backend-py312 .

# 构建成功的标志(失败则构建直接报错,不会出坏镜像):
#   "myapp import OK"
#   "HDFS-Kerberos OK"
```

> 若必须用容器法(方式 A,不用 Dockerfile):照 `./fix/交接/文档/行内build操作手册.md` §1-§3,**并在 commit 前执行** `echo 'export PATH=/opt/appenv/bin:$PATH' >> /etc/profile.d/cube312.sh`(否则 K8s 里 PATH 不含应用环境,全挂)。

## 6. K8s 切换(6 步,每步有检查)

```bash
# ⓪ 先保存当前镜像引用(回退基线, 比写死旧 tag 更准)
OLD_IMG=$(kubectl -n infra get deploy kubeflow-dashboard -o jsonpath='{.spec.template.spec.containers[0].image}')
echo "当前镜像: $OLD_IMG"   # 回退 §7 直接用它

# ① 更新 ConfigMap(必须!否则 py3.12 启动即崩; kubectl 在 master1 执行)
kubectl -n infra delete configmap kubeflow-dashboard-config 2>/dev/null
kubectl -n infra create configmap kubeflow-dashboard-config \
  --from-file=config.py=install/kubernetes/cube/overlays/config/config.py \
  --from-file=entrypoint.sh=install/kubernetes/cube/overlays/config/entrypoint.sh \
  --from-file=project.py=install/kubernetes/cube/overlays/config/project.py
kubectl -n infra get configmap kubeflow-dashboard-config -o yaml | grep -c "import importlib"   # 期望 >=1

# ② 换 4 个 deployment 的 tag
for d in kubeflow-dashboard kubeflow-dashboard-schedule kubeflow-dashboard-worker kubeflow-watch; do
  kubectl -n infra set image deployment/$d kubeflow-dashboard=10.240.125.39/cube-studio/kubeflow-dashboard:app-p312-v1
done
# ②' init 容器 busybox 若引用的是开发 harbor(192.168.11.12), 生产节点拉取失败时同步换:
#   kubectl -n infra set image deployment/kubeflow-dashboard wait-mysql=10.240.125.39/cube-studio/busybox:1.36.0 wait-redis=10.240.125.39/cube-studio/busybox:1.36.0
#   (名称以 get deploy -o yaml 实际 initcontainer 名为准)

# ③ rollout
kubectl -n infra rollout status deployment/kubeflow-dashboard
kubectl -n infra rollout status deployment/kubeflow-dashboard-schedule
kubectl -n infra rollout status deployment/kubeflow-dashboard-worker
kubectl -n infra rollout status deployment/kubeflow-watch

# ④ 观察 10 分钟(8 项全绿才算完成)
kubectl -n infra get pods | grep -E "dashboard|watch"          # 4 个 1/1 Ready
kubectl -n infra logs deployment/kubeflow-dashboard --tail=100 | grep -iE "traceback|error"
#   期望:无 Traceback;("Duplicate column" 属正常!)
kubectl -n infra exec deploy/kubeflow-dashboard -- curl -s localhost/health     # OK
# schedule/worker 探针看 get pods 状态即可

# ⑤ 通知交接人进行功能抽验(登录/管道/数据集/HDFS 用例)
# ⑥ 达标后交付:后端镜像 tag、pip freeze、rpm -qa 清单
```

## 9. 红线(每条都踩过坑)

1. **必须先更新 ConfigMap 再换 tag**(顺序反了会先崩一波)
2. 任何 `ResolutionImpossible / No matching distribution` → **命令顺序错了**(对照 行内build操作手册 §4 对照表),截图交回
3. 不要安装 krbcontext/sasl/gmssl(死依赖,已删除)
4. `Duplicate column name` 是设计内输出,忽略
5. 不要自行更换镜像内 python 路径/版本结论(/opt/appenv 是基座 python3.12 建的 venv)
