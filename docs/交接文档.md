## 一、项目概述

Cube Studio 是一站式云原生机器学习平台，本项目基于[腾讯音乐开源版本](https://github.com/tencentmusic/cube-studio)进行二次开发，针对**内网麒麟信创 (Kylin V10) 环境**做了大量适配改造和功能增强。

### 1.1 上游关系

| 项目 | 说明 |
|------|------|
| 上游仓库 | https://github.com/tencentmusic/cube-studio |
| 基线版本 | 2026.03.01 版本（推断，基于 docker-compose 中镜像 tag） |
| 二开仓库 | 内网 Git，分支 `final` |
| 代码量 | 约 300+ MB（含制品），纯代码约 50MB |

### 1.2 运行环境

| 项目 | 说明 |
|------|------|
| OS | 麒麟 V10 SP3 (Kylin Linux Advanced Server 10) |
| 架构 | x86_64 only |

| 容器运行时 | Docker (原版 containerd 已废弃，改用 Docker) |

**HDFS API 端点**：
```
GET  /hdfs_browser/api/get_config      — 获取 HDFS 配置信息
GET  /hdfs_browser/api/test_connection — 测试连接
GET  /hdfs_browser/api/get_config_full — 完整配置 (admin only)
POST /hdfs_browser/api/save_config     — 保存配置 (admin only)
GET  /hdfs_browser/api/list_dir        — 浏览目录（分页）
GET  /hdfs_browser/api/search          — 模糊搜索路径
```

**HDFS 客户端特性**：
- Kerberos (keytab) 认证
- 连接缓存 10 分钟（避免重复 kinit）
- Parquet schema 读取优化：尾部 footer 读取（1MB）代替全文件下载
- 支持分区列自动检测（dt/partition_dt/date/p_date/day/fdate）
- 下载支持断点续传和进度回调
- 配置持久化到 JSON 文件（`hdfs_config.json`）

### 3.4 高可用 (HA) 改造

**单点 → 高可用：任意 Master 宕机，用户和运维无感知。**

| 文件 | 操作 | 说明 |
|------|------|------|
| `install/kubernetes/metallb-native.yaml` | **新建** | MetalLB L2 模式 |
| `install/kubernetes/metallb-config.yaml` | **新建** | IP 池配置 |
| `install/kubernetes/apiserver-lb.yaml` | **新建** | API Server LoadBalancer Service |
| `install/kubernetes/virtual.yaml` | **新建** | Istio VirtualService + retry |
| `install/kubernetes/cube/base/pdb.yaml` | **新建** | 4 个 PodDisruptionBudget |
| `install/kubernetes/cube/base/deploy-backend.yaml` | 修改 | replicas: 1→2, podAntiAffinity, preStop, 探针 |
| `install/kubernetes/cube/base/deploy-frontend.yaml` | 修改 | replicas: 1→2, podAntiAffinity, 探针 |
| `install/kubernetes/cube/base/deploy-worker.yaml` | 修改 | replicas: 1→2, liveness 探针修复 |
| `install/kubernetes/cube/overlays/config/config.py` | 修改 | ENABLE_PROXY_FIX=True, 连接池缩小 (300→100) |
| `install/kubernetes/cube/overlays/config/entrypoint.sh` | 修改 | create-admin/init 加 `\|\| true` 防 CrashLoopBackOff |
| `install/docker/config.py` | 修改 | ENABLE_PROXY_FIX=True |
| `install/docker/entrypoint.sh` | 修改 | create-admin/init 加 `\|\| true`, Redis 分布式锁 |

**关键技术决策**：
- API Server HA：MetalLB Service (L2 ARP) 而非 keepalived+HAProxy（避免装系统包）
- Worker kubelet 连接 VIP (192.168.11.200)，Master 宕机 Worker 不丢失连接
- Master kubelet 连各自本地 apiserver (127.0.0.1)，避免 hairpin NAT
- kubectl 配置指向 VIP，任一 Master 宕机仍可用

**详细文档**：`docs/CubeStudio-HA-改造完整文档.md`

## 六、关键运维操作

### 6.1 集群重启

参考 `restart/README.md`，注意启动顺序：
1. MySQL (StatefulSet) → 确认 ready
2. Redis (StatefulSet) → 确认 ready
3. kubeflow-dashboard (backend) → 确认 ready（会执行 db upgrade）
4. kubeflow-dashboard-schedule (celery beat) → 确认 ready
5. kubeflow-dashboard-worker (celery worker) → 确认 ready
6. kubeflow-watch (工作流监控) → 确认 ready
7. kubeflow-dashboard-frontend (nginx) → 确认 ready

### 6.2 数据库迁移

迁移通过 entrypoint.sh 自动执行，使用 Redis 分布式锁确保多 Pod 不会并发执行。

手动执行迁移：
```bash
kubectl exec -it deployment/kubeflow-dashboard -n infra -- bash
export FLASK_APP=myapp:app
myapp db upgrade
myapp init   # 重新初始化种子数据（会跳过已存在的记录）
```

### 6.3 查看日志

```bash
# 后端日志
kubectl logs -f deployment/kubeflow-dashboard -n infra

# Celery worker 日志
kubectl logs -f deployment/kubeflow-dashboard-worker -n infra

# Celery beat 日志
kubectl logs -f deployment/kubeflow-dashboard-schedule -n infra

# 工作流监控日志
kubectl logs -f deployment/kubeflow-watch -n infra
```

### 6.4 平台配置管理

通过 Web 界面 → "平台配置" 页面（仅 admin）：

- "保存" → 仅对新 Pod 生效
- "更新所有现存Pod" → 触发滚动重启，对已有 Pod 生效

### 6.5 HDFS 配置管理

通过 Web 界面 → "HDFS 配置" 页面（仅 admin）：
- 配置 HDFS URL / keytab 路径 / principal / base_path
- "测试连接" → 验证 Kerberos 认证是否通过
- 配置保存到 `hdfs_config.json`（持久化，Pod 重启不丢失）

## 八、核心技术决策记录

### 决策 1：联网操作 100% 收敛到 base 镜像
**背景**：内网环境无法访问 yum 源和 pypi。
**决策**：所有 yum/pip/wget 操作集中在 `Dockerfile-base.kylin`，在联网环境构建一次并推送到内网 Harbor。生产镜像 `Dockerfile.kylin` 只做 COPY 操作。
**影响**：依赖变更时需要在联网环境重新构建 base 镜像。

### 决策 2：MetalLB L2 而非 keepalived+HAProxy 做 API Server HA
**背景**：麒麟系统不容易安装额外系统包。
**决策**：使用 MetalLB 原生 K8s 方案，L2 模式 ARP 实现 VIP 漂移。
**影响**：API Server 证书 SAN 必须包含 VIP (192.168.11.200)。

### 决策 3：HDFS 使用 hdfs 库 (KerberosClient) 而非 WebHDFS
**背景**：内网 HDFS 集群使用 Kerberos 认证。
**决策**：使用 Python `hdfs` 库的 KerberosClient，配合 keytab 文件进行认证。
**影响**：需要 keytab 文件和 krb5.conf 配置，Pod 启动后需 kinit。

### 决策 4：Parquet Schema 读取优化（尾部读取）
**背景**：Parquet 文件可能很大（数 GB），全文件下载开销太大。
**决策**：只读取文件尾部 1MB，从中解析 footer_length + schema metadata。如果 footer 超出尾部范围，回退到全文件下载。
**影响**：Schema 获取从 O(文件大小) 降低到 O(1) 时间。

### 决策 5：全局配置用 DB 单例表而非 config.py
**背景**：hostAliases 需要 admin 在 UI 上动态配置，不能每次修改 config.py + 重启 Pod。
**决策**：PlatformConfig 表存储配置，`_load_platform_config()` 懒加载到 `app.config`，修改后通过 `_refresh_config()` 刷新运行时缓存。
**影响**：`py_k8s.py` 的 `make_pod()` 需要同时读取 config.py 的 HOSTALIASES 和 PlatformConfig 的配置，合并后注入 Pod。

## 九、已知问题与注意事项

### 9.1 产品级问题

1. **麒麟 container 路由问题**：Kylin V10 从 Docker hub 拉取 image 有时失败，可能与 CA 证书缺失有关。解决方法：关闭 SSL 验证或从内网 Harbor 拉取。

2. **glibc 版本**：麒麟 V10 SP1 的 glibc 是 2.28，部分工具需要 >= 2.29。需要使用 musl 静态编译版（如 cc-switch-cli）。

3. **麒麟系统缺少编译工具链**：gcc/gcc-c++/make 需要显式安装，build-essential 不存在。

4. **麒麟系统没有 OpenSSL 3.x**：官方源只有 1.1.1。需要用 conda 安装。

5. **Matlab/RStudio Notebook 镜像**：标记为 `(todo)`，尚未完成。

### 9.2 运维问题

6. **Celery watch 探针特殊逻辑**：`kubeflow-watch` 的 liveness 探针在每天凌晨 3 点自动失败，触发 Pod 重启（释放 supervisor 子进程积压）。这是预期行为，不是 bug。

7. **entrypoint.sh 中的 `|| true`**：`fab create-admin` 和 `myapp init` 如果失败（权限已存在、数据已存在）不阻塞启动。这是 HA 改造的一环：避免 CrashLoopBackOff。

8. **数据库连接池缩小**：HA 多副本时从 300→100，防止撑爆 MySQL max_connections。

9. **container 环境内可能缺少 buildx**：`Dockerfile-base.kylin` 构建时需要 buildx 支持 `--platform`。

### 9.3 安全问题

10. **SECRET_KEY 硬编码**：`config.py` 中 `SECRET_KEY = "\2\1thisismyscretkey..."` 是硬编码的，**需要在上线前改为从环境变量读取**。

11. **admin 密码默认值**：`entrypoint.sh` 中创建 admin 密码为 `admin`，**建议上线后修改**。

## 十二、常见排障场景

### 12.1 新 Pod 创建后无法解析内网域名
**排查**：检查 "平台配置" 页面的 hostAliases 是否正确。新 Pod 会在 `/etc/hosts` 中注入这些映射。

### 12.2 HDFS 连接失败
**排查**：
1. 检查 keytab 文件是否存在于 Pod 内指定路径
2. 检查 krb5.conf 配置是否正确
3. 在 "HDFS 配置" 页面点击"测试连接"
4. 检查 HDFS 集群是否可达

### 12.3 数据库迁移失败导致 Pod 重启
**排查**：
1. 查看 entrypoint.sh 日志中 `db upgrade` 的输出
2. 检查是否多个 Pod 同时执行（Redis 锁超时？）
3. 手动 exec 进 Pod 执行 `myapp db upgrade` 查看具体错误

### 12.4 Celery worker 不健康
**排查**：
1. `celery -A myapp.tasks.celery_app:celery_app inspect ping -d worker@$HOSTNAME`
2. 检查 Redis 连接：`redis-cli -h $REDIS_HOST -p $REDIS_PORT -a $REDIS_PASSWORD PING`
3. 查看 worker 日志是否有任务失败堆栈

### 12.5 前端页面 404
**排查**：
1. 检查前端 nginx 是否正常: `curl http://kubeflow-dashboard-frontend.infra/frontend/`
2. 检查后端是否正常: `curl http://kubeflow-dashboard.infra/health`
3. 如果后端正常但前端代理失败，检查 nginx default.conf 中的 proxy_pass
