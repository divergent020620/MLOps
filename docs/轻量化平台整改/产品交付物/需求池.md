## 怎么读这张表

| 列 | 谁填 | 说明 |
|---|---|---|
| **ID** | 产品 | 模块前缀 + 序号，作唯一标识 |
| **用户故事** | 产品 | "作为〈角色〉，我希望〈做什么〉，以便〈获得什么价值〉" |
| **验收标准** | 产品 | 判断做没做完的客观条件，**必须可判定** |
| **优先级** | **产品** | MoSCoW：必须(M) / 应该(S) / 可以(C) / 不做(W) |
| **阶段** | 产品 | 对应后续的交付批次（一期 / 下一期 / 二及以后） |
| **估算** | **研发** | 工时，**产品不估** |
| **状态** | 研发 | 待开发 / 进行中 / 待验收 / 已完成 |

**两条规矩**：
1. **优先级是产品定的，估算是研发定的。** 越界就会失真。
2. **验收标准写不清楚的需求，不许进开发。** 写不清楚通常意味着需求本身没想明白。

### 优先级怎么定

不是"都重要"。问自己一句话：**如果这一版只能做一条，做哪条？** 答不上来就是没排。

- **必须(M)**：不做这版就没有意义
- **应该(S)**：不做会明显影响体验，但能上线
- **可以(C)**：有更好，可以下一版
