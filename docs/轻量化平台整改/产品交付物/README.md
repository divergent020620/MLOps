## 一、产品经理到底产出什么

不用记太多，产品经理的产出物就四层，每层回答一个问题：

```
① 战略层  我们为什么做这个、做到什么算成功      → 产品愿景 / 路线图 / 成功指标
② 范围层  这一版做什么、明确不做什么            → PRD（产品需求文档）
③ 交付层  具体要做什么、怎么算做完了            → 需求池 / 用户故事 / 验收标准
④ 验证层  做完之后效果怎么样、要不要调方向      → 数据看板 / 复盘
```

**关键点：这四层是"答问题"，不是"写文档"。** 文档只是载体。你完全可以不写文档，但你必须能回答这四个问题——否则研发会一直来问你，或者自己猜。

每一层对应的产出物：

| 层 | 产出物 | 回答什么问题 | 主要读者 | 什么时候更新 |
|---|---|---|---|---|
| ① | **产品愿景** | 一句话：这是个什么产品，给谁 | 领导 | 基本不变 |
| ① | **路线图（Roadmap）** | 分几个阶段、每阶段交付什么 | 领导 + 团队 | 每季度/每阶段 |
| ① | **成功指标** | 怎么判断我们做成了 | 领导 | 每阶段开始时定，结束时看 |
| ② | **PRD** | 做什么、不做什么、为什么 | 研发 + 测试 + 领导 | 需求变更时 |
| ③ | **需求池（Backlog）** | 待办的需求清单，排序后的 | 研发 | 持续 |
| ③ | **用户故事 + 验收标准** | 一条需求的"什么"和"怎么算完成" | 研发 + 测试 | 开发前定 |
| ④ | **数据看板 / 复盘** | 用了没有、好用没有 | 领导 + 自己 | 阶段结束 |

### 六件最容易搞错的事

1. **PRD 不是需求清单。** PRD 里最重要的是**暂缓 / 非目标**（哪些晚点做、哪些不做）——范围失控是项目失败的头号原因，而"不做什么"只有产品经理能拍。
2. **验收标准必须可判定。** "体验流畅"不是验收标准；"单节点宕机后，Jupyter 里的文件仍可正常读写"才是。
3. **优先级不是"都重要"。** 优先级是一句取舍：**如果只能做一个，做哪个**。都重要等于没排。
4. **"暂缓"和"不做"是两回事，方向正好相反。**

   | | 含义 | 怎么做 | 验收标准 |
   |---|---|---|---|
   | **暂缓** | 认可它的价值，但现在做不成或不该先做 | **留口子**：别删、别清、保持可恢复 | 将来能一键恢复 |
   | **不做** | 决定永久不要 | **清理干净**：连代码带数据 | 重启后不再出现 |

   **对暂缓的做清理、对不做的做预留，都是错的方向**——而且做反了通常会到很晚才发现。

   本项目的实例：**大模型相关**（Chat/RAG/知识库 + `xinference` 模板）是**非目标**（定位上不做）→ 可清理；
   **流水线**是**暂缓**（会做，只是排期在后）→ 必须保留；而**训练 / HDFS 数仓浏览已完成**（见 PRD 10.3）。
5. **别用环境现状推断需求。** 开发/测试环境的"没部署""没使用量""没有 GPU""没有 HDFS"，**都不能推出"这个功能不需要"**——它们只说明"这个环境部署了什么"。

   > **环境现状 ≠ 产品需求。** 更要紧的是：本项目**行内开发、行内上线**，
   > 开发环境里看不到的东西**不代表行内没有**——拿它当"项目缺口"会白砍功能、白估工作量。
6. **"被替代"要单独记一笔。** 一个功能被另一个功能顶掉了，既不是"暂缓"也不是"不做"——是**已经有别的方案满足了这个需求**。

   本项目：**ETL 流水线已被 HDFS 取数替代**。

   为什么要记：不写下来的话，下一个版本很容易**照着原样再做一遍**，而能力其实早就有了。**"谁替代了谁"必须落在文档里。**

## 三、怎么用这套东西推进工作

### 1. 定方向（用路线图）
拿 `路线图与成功指标.md` 找领导过一遍：**五阶段、每阶段交付什么、怎么算成**（该文件第〇章已与官方《人员安排与时间计划》对齐）。这一步不通过，后面全是白做。

重点让领导拍两件事：
- **阶段性取舍**——比如"只交付能做实的 5 个功能、中间件服务排下一期"，这是产品决策，不是技术决策；
- **缺口补位**——⚠️ **存储单点治理在官方五阶段里没有位置**（见该文件第〇章），需要明确插进哪个阶段。

### 2. 对范围（用 PRD）
拿 `PRD-通用小模型平台.md` 和研发过：重点过**第 3.2 / 3.3 节**（暂缓 vs 不做）和**第 5 章产品范围**。研发最容易在这一步问出真问题——比如"这个功能本期不交付了，但 XX 团队还在用它，怎么办"。这些回答要回写进 PRD。

### 3. 排期（用需求池）
拿 `需求池.md` 和研发一起估时、排序。**优先级那列是产品定的，估算那列是研发定的**——不要让研发定优先级，也不要让产品估工时。

### 4. 验收（用验收标准）
每条需求都有验收标准，做完直接照着判。**不要用"感觉好了"验收**——这是产品经理最容易被研发和领导两头夹的地方，验收标准就是你的护身符。

### 5. 复盘（用成功指标）
阶段结束对着 `路线图与成功指标.md` 里的指标表看一遍：达到了没有、没达到是为什么、下阶段怎么调。

## 四、快速上手：每次开会前问自己这五个问题

1. **这次会要谁拍什么板？**（没有要拍板的会就不用开）
2. **我给的选项是几个？分别的代价是什么？**（只给一个方案 = 没做产品工作）
3. **做完之后怎么判断成没成？**（验收标准）
4. **这次明确不做什么？**（非目标）
5. **有什么是我还没搞清楚、但会影响结论的？**（开放问题）

这五个问题，就是本目录所有文档的骨架。
