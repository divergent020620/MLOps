## 一、结论先行

我们要把 Cube Studio 从「一站式 MLOps 大平台」收敛成**通用小模型平台**——**只做小模型、不做大模型**；一期交付 5 个功能（登录注册 / 用户管理 / Jupyter / 推理服务 / 取数存数），其余排后续版本届时恢复。

> **平台定位一句话**：**把行内既有的 YARN 算力与 HDFS 数仓接进来，给算法同事一个统一入口**——不是"再建一个 MLOps"。
> 项目周期 2026.09 - 2026.12（V1.0 投产），2027 起迭代。与官方计划的对齐见第九章。

你说的三件事，**不是同一层的问题**，所以不能并列推进：

| # | 诉求 | 它实际是什么问题 | 不做的后果 | 建议优先级 |
|---|---|---|---|---|
| 1 | 隔离按项目而非按用户 | **产品正确性问题** | 协作模式不成立；配额/审计/归档无处挂 | **P1（但有时间窗）** |
| 2 | NFS 单点迁到 MinIO | **可用性与数据风险问题** | 盘满或 master1 挂 → 全平台停；无备份 → 数据不可恢复 | **P0** |
| 3 | 拆成多 pod 独立迭代 | **交付效率问题** | 改一行要重建镜像、重启 4 个 deployment | **P2（有一处低成本切入点）** |

**给领导的三句话：**

1. **存储要修，答案比"迁到 MinIO"更具体：MinIO 自己就得先改成分布式。** MinIO 现在跑在一块单点盘上——它的 PV 是 `hostPath: /data/k8s/kubeflow/minio`（`install/kubernetes/argo/minio-pv-pvc-hostpath.yaml:13-14`）。**不先改分布式，把数据搬进它就只是换个地方放，单点一点没少。** 完整答案是「**分布式 MinIO（6 节点纠删码）+ JuiceFS 补 POSIX 层**」——Jupyter 工作区是文件系统语义，对象存储装不下。两套清单仓库里都现成，只是从未部署；卡点是节点标签 / StorageClass / CSI 这些前置没做（见 4.4）。

2. **隔离改造现在做最便宜，以后做最贵。** 现在的物理隔离是 `subPath={username}`（`py_k8s.py:916-917`），同一用户在任意项目看到的都是同一个 `/mnt/{username}`。好消息是**当前开发环境没有真实用户数据**——DB 里 `run` 表 0 条，notebook 6 个、dataset 5 个都是测试数据。改动只有 14 个文件、每个文件 1-5 行，**在本环境改零迁移成本**。

> ✅ **已确认（2026-09-24）：行内环境没有存量数据在跑。** 所以隔离改造确实是**零迁移成本**——**抓紧这个窗口，别等有数据了再做。**

3. **"拆成多个 pod"有 80% 的收益可以用 20% 的成本拿到，但那个 20% 不是你想的那件事。** 现在瓶颈不是"后端是一个 pod"——它已经是 4 个 deployment 了。瓶颈是**这 4 个 deployment 用同一个镜像、同一份 ConfigMap、同一次全量加载**。先做「角色化加载 + 把数据库迁移从 web 启动流程里搬走」，就能立刻让重启变快；真正拆成微服务是后面的事，不建议现在做。

**建议节奏（三阶段，总量约 3-4 个月，团队现有人力）：**

| 阶段 | 时间 | 做什么 | 为什么这个顺序 |
|---|---|---|---|
| 一 · 止血 | 1-2 月 | **分布式 MinIO + JuiceFS** + 持久化 Redis | 唯一会丢数据的事；存储底座定下来，后面才谈得上迁数据 |
| 二 · 正确性与瘦身 | 2-3 月 | 项目级隔离 + 隐藏不交付模块（含低代码/编排类）+ 拆分 L1.5 | 隔离要赶在真实数据进来之前；先收窄范围再拆，避免拆完再改一遍 |
| 三 · 交付效率 | 2-3 月 | 拆分 L1 / L2 | 视阶段一、二的真实效果再定；L3 暂缓 |

## 三、诉求一：隔离从「按用户」改为「按项目」

### 3.1 现状：确实是按用户，而且三层都错了

**第一层：物理隔离（卷）——按用户**

```python
# myapp/utils/py/py_k8s.py:916-917
"mountPath": os.path.join(mount, username),   # /mnt/{username}
"subPath": username                           # {username}
```

所有项目共用一个 PVC `kubeflow-user-workspace`，而**每个 namespace 的 PV 都指向同一个 hostPath** `/data/k8s/kubeflow/pipeline/workspace`（`py_k8s.py:2359-2360`，`config.py:777`）。隔离完全靠 `subPath`。

后果：**同一用户在项目 A 和项目 B 里，挂载的是同一个目录，文件完全互通**；反过来，项目内两个成员**看不到彼此的文件**，无法协作。

**第二层：列表可见性——一半项目级、一半用户级，不一致**

| 视图 | 过滤口径 | 位置 |
|---|---|---|
| Pipeline | ✅ 项目成员 | `view_pipeline.py:62-75` |
| Service / InferenceService | ✅ 项目成员 | `view_serving.py:37-46`、`view_inferenceserving.py:112-119` |
| NNI / ETL_Pipeline / Training_Model | ✅ 项目成员 | `view_nni.py:50-64` 等 |
| **Notebook** | ❌ **按创建人** | `view_notebook.py:45-51` |
| **Docker** | ❌ **按创建人** | `view_docker.py:38-44` |
| **Job_Template** | ❌ **全局**（项目过滤被注释） | `view_job_template.py:44-52` |

注意 `Notebook` **本身有 `project_id` 字段**（`model_notebook.py:30`），却按 `created_by_fk == g.user.id` 过滤——**不是模型缺字段，是查询写错了**。

**第三层：命名空间——默认全局共享**

`Project.namespace` 支持从 `expand['namespace']` 读每个项目的命名空间，但默认回落到全局常量 `jupyter`/`pipeline`/`service`/`automl`（`model_team.py:76-94`，`config.py:719-729`）。也就是说**开箱即用状态下，所有项目挤在同一个命名空间里**。

### 3.2 为什么这是产品问题，不只是技术问题

| 受影响的产品能力 | 当前状态 |
|---|---|
| 团队协作（项目内共享数据/模型） | ❌ 做不到，只能各存各的 |
| 项目维度的资源配额 | ❌ 字段存在但不生效：`Project_User.quota`（`model_team.py:229`）只在 `view_team.py:328-356` 做格式校验，无运行时强制 |
| 项目维度的审计与归档 | ❌ 做不到，只能按用户清理 |
| 项目维度的成本核算 | ❌ 无挂载点 |
| 前端项目切换 | ❌ **React 前端没有项目切换器/项目页**，项目只能在后端 FAB 管理页维护（前端仅 `PipelineList.tsx` 显示了一个 project 列） |

**一句话**：现在产品里"项目"是个装饰性概念——DB 有表、有 `project_id` 字段、有成员关系，但**没有任何一条业务规则真正以项目为单位生效**。

### 3.3 三个方案选项

| 方案 | 内容 | 改动量 | 能解决什么 | 遗留 |
|---|---|---|---|---|
| **A. 最小** | 只把卷 `subPath` 从 `username` 改为 `project_id` | ~4 文件 | 项目间数据隔离；项目内可协作 | 列表可见性仍按用户；命名空间仍共享；静态文件越权 |
| **B. 完整（推荐）** | A + 统一列表过滤口径 + 静态文件访问校验 + 命名空间按项目 | ~14 文件 | 上述全部 | 配额仍未强制；前端仍无项目切换 |
| **C. 多租户** | B + 每项目独立命名空间 + `ResourceQuota`/`LimitRange` + 配额强制 | ~25 文件 + 前端 | 真正的多租户 | **不是不做，是排到后续版本**（见下）。当前无多团队诉求，且要先有 B 和用量计量 |

> ⚠️ **方案 C 已排入后续版本（阶段四），不是被否决。** 所以本期做 B 时必须**按"可独立命名空间"的方式设计**——即使本期所有项目仍共用一个命名空间，也要让 `Project.namespace` 的每项目覆盖能力是通的。这样阶段四加 `ResourceQuota` 是加法；否则是重构。
> 产品侧的表述见 `产品交付物/PRD-通用小模型平台.md` 第 3.2 节。

**已有的设计可以直接复用**：同目录下的 `项目隔离-设计方案.md` 和 `项目隔离-实施计划.md`（2026-08-11）已经把方案 B 拆成了 12 个任务、14 个文件，含具体 diff。**这两个文档从未实施**——本次核对确认 `py_k8s.py:884` 的函数签名仍是 `get_volume_mounts(volume_mount, username)`，全仓没有任何 `KFJ_PROJECT_ID`。

### 3.4 建议

**做方案 B，并且复用已有 plan。**

四个必须补充的细节（原 plan 没覆盖或不够）：

1. **`Task` 表没有 `project_id`**，只能通过 `task.pipeline.project_id` 间接取（`model_job.py:512`）。`RunHistory`、`Workflow` 同样没有。这是"运行时实体不带项目"的结构性缺口，做审计/配额时一定会撞上。
2. **静态文件访问校验目前是关闭的**（`myapp/__init__.py:320` 被注释掉，而且原本就是按 `g.user.username` 判断的）。改成项目隔离后必须同步打开并改为按 `project_id` 校验，否则容器内隔离了、HTTP 层还漏着。
3. **`get_volume_mounts` 是 `@staticmethod`，靠调用方传 `username` 展开卷**（`py_k8s.py:884`）。这意味着**传错参数就会挂到别人的卷上**——改成 `project_id` 后这个风险从"越权到别的用户"变成"越权到别的项目"，需要在服务端根据对象自身推导 `project_id`，而不是信任调用方传入。
4. **一个好消息：挂载解析器已经支持只读共享卷，不需要新建机制。** `get_volume_mounts` 除 `(pvc)` 外还支持 `(pvc-share)`（`:920-934`）、`(pvc-ro)`（`:936-951`）、`(nfs)`/`(nfs-ro)`（`:953-1003`）、`(storage)`、`(hostpath)`、`(configmap)`、`(secret)`、`(memory)`。所以"项目内共享目录给只读、个人目录给读写"这类需求，**改配置字符串即可**，不用写新代码。

**时间窗提醒**：现在 DB 里 pipeline run = 0、notebook 6 个（都是 `admin-*` 测试实例），**没有真实业务数据**。方案 B 现在做是纯代码改动；等真实数据进来，还要额外做一次全量 `/mnt/{username}/` → `/mnt/{project_id}/` 的目录搬迁和用户脚本路径修正（原 plan 里明确提到"用户脚本中硬编码的 `/mnt/{username}/` 需要更新"）。

## 四、诉求二：存储从 NFS 迁到 MinIO

### 4.1 结论：MinIO 必须改成分布式——但它不是唯一的短板

方向完全对。**MinIO 现在自己就跑在 NFS 上**，所以它必须改成分布式（多节点 + 纠删码）；否则"把数据迁到 MinIO"只是把数据从一块单点盘，挪到一个更脆的单点上。

证据链（实测）：

```
MinIO 自己的 PV
  └─ hostPath: /data/k8s/kubeflow/minio                     ← argo/minio-pv-pvc-hostpath.yaml:13-14
       └─ 500Gi, accessModes: ReadWriteOnce, storageClassName: ""   ← :10-12, :24-25, :33
            └─ /data/k8s  →  软链  →  /bdm/share_bdm
                 └─ 服务器1 的 vdb（一块 100G 本地盘），NFS 导出 *(rw,no_root_squash,async)
                      └─ 5 台机器全部挂载
```

MinIO 是 **单副本 + RWO PVC**（`argo/minio.yaml`，1 replica），而 `/bdm` 就是服务器1 的一块本地盘——**单点是双重的**：单个 pod，加单块盘。

**但要提醒范围：分布式 MinIO 只能接住"对象语义"的那部分数据。** Jupyter 工作区是 POSIX 语义（随机写、文件锁、mmap），对象存储装不了。所以真正要做的是**两层**：

```
JuiceFS（POSIX 层，CSI）── 对象后端 ──▶  分布式 MinIO（6 节点纠删码）
       │                                    └── Redis（元数据）
       ├── Jupyter 工作区 /mnt
       ├── 数据集
       ├── 模型归档
       └── AIHub
```

**好消息：这套架构不用新设计——两份清单仓库里都现成，只是从未部署**（见 4.4）。

### 4.2 真实风险盘点

| # | 风险 | 事实 | 等级 |
|---|---|---|---|
| 1 | **存储超卖** | 15 个 PV 声称合计 5212Gi，底下是同一块剩 45G 的盘 → **超卖 52 倍**。PV 的 size 是装饰性的 | 🔴 |
| 2 | **权限敞开** | NFS 导出 `*(rw,no_root_squash)` —— 任意主机可挂载且拥有 root 映射 | 🔴 |
| 3 | **无备份无快照** | 未发现任何备份任务；hostPath 无快照能力 | 🔴 |
| 4 | **与智算平台的合并工期不受我方控制** | 2027 Q1 要接入智算平台；对方排期若延后，我方合并相关交付与验收会一起延后 | 🟠 |
| 5 | **MinIO 凭证硬编码** | `MINIO_ROOT_USER=minio` / `MINIO_ROOT_PASSWORD=minio123`（`minio.yaml`） | 🟠 |
| 6 | **Redis 无持久化** | emptyDir，同时是 Celery broker + 缓存 + **DB 迁移分布式锁** | 🟠 |

### 4.3 数据清单：谁存在哪、能不能上 MinIO

| 数据类别 | 现存储 | 代码路径 | 能上 MinIO？ |
|---|---|---|---|
| Argo 归档的**日志与指标** | **MinIO** bucket `mlpipeline`（MinIO 目前的全部用途） | 读：`view_workflow.py:499-569`；配置：`install-3.4.3-all.yaml:1125-1136` | 已在 |
| **流水线步骤间传递的数据** | **NFS**（`/mnt/{creator}/...`），**不走 MinIO** | `view_pipeline.py:244,303-306,419` | ⚠️ 需重新设计（见 4.6） |

> **对"MinIO 只承担了 Argo 相关的东西"这句的精确化**：更准确的说法是——**MinIO 只承担了 Argo 的日志/指标归档**。连流水线步骤之间传递的数据都不走 MinIO，而是靠共享 NFS 路径约定（`/mnt/{creator}/...`）。`Task.outputs` 字段的注释写着 "copied to minio"，但**这个写入逻辑在本仓库里不存在**（`model_job.py:538`）。所以 MinIO 的实际职责比"Argo 相关"还要窄。

**为什么 Jupyter 工作区不能直接上 MinIO**：对象存储没有 POSIX 语义。JupyterLab 会实时随机写入 `.ipynb`、建 conda 环境、clone git 仓库、用 mmap 和文件锁。用 S3 API 挂载（s3fs/goofs 那类）会遇到一致性和性能问题，属于**明确不推荐**的做法。

> ⚠️ **一个容易低估的成本**：`STORE_TYPE=""`（`config.py:787`），而且 `myapp/utils/store/` **这个目录在仓库里根本不存在**——但 `view_dataset.py:370` 有一个 `importlib.import_module(f'myapp.utils.store.{store_type}')` 的分支。也就是说对象存储这条路**从来没跑通过，代码是照抄上游的**。真要走 MinIO，**不是改配置，是要新建一整个存储抽象层**。`STORE_CONFIG` 里现在还是腾讯云 COS 的模板（`config.py:788-796`）。

### 4.4 落地路径：仓库里已备好「分布式 MinIO + JuiceFS」

两套清单都在仓库里，只是从未部署：

| 清单 | 位置 | 是什么 |
|---|---|---|
| **分布式 MinIO** | `install/kubernetes/minio/cluster/` | **6 副本** StatefulSet，6 个独立端点（`minio-0..5.minio.infra.svc`）→ 纠删码模式；含 6 个 PV + StorageClass `local-minio` |
| **JuiceFS CSI 层** | `install/kubernetes/juicefs/` | StorageClass `juicefs-sc`（provisioner `csi.juicefs.com`）+ 6 个 namespace 的 PV/PVC 替换件 |

**两条清单是配套的**：`juicefs-decive-of-k8s/juicefs-sc.yml:10-11` 的 Secret 里写着 `storage: "minio"`、`bucket: "http://…/juicefs"`——**JuiceFS 的对象后端就是 MinIO**。

而且 JuiceFS 版 PV 与现有 hostPath 版是**逐个同名对应的替换件，不是新增件**：

| hostPath 版（现役） | JuiceFS 版（未部署） |
|---|---|
| `pv-pvc-jupyter.yaml` → PV `jupyter-kubeflow-user-workspace` | `jupyter-pv-pv-with-juicefs.yml` → **同名 PV**，driver `csi.juicefs.com`，`mountOptions: subdir=kubeflow/pipeline/workspace` |
| `pv-pvc-{infra,pipeline,service,kubeflow}.yaml` | `{infra,pipeline,service,kubeflow}-pv-pvc-with-juicefs.yml` |

连 `subdir` 都与现有路径对齐（`kubeflow/pipeline/workspace`）——是照着现有布局做的替换设计。**所以这件事的工作量主要在"部署 + 重新指向"，不在"设计"。**

#### 但当前集群部署不了——4 个机制性障碍（已实测）

| # | 障碍 | 实测结果 | 后果 |
|---|---|---|---|
| 1 | **集群里没有任何 StorageClass** | `kubectl get sc` → `No resources found` | 分布式 MinIO 清单的 `storageClassName: local-minio` 绑不上 |
| 2 | **没有任何节点有 `pvrole` 标签** | `kubectl get nodes` → 5 台全 `<none>` | 6 个 PV 的 nodeAffinity 永远匹配不到 → PV 永久 Pending |
| 3 | **没有 CSI 驱动** | `kubectl get csidriver` → `No resources found`；juicefs pod 0 个 | JuiceFS 的 PV 无法挂载 |
| 4 | **清单指向上游环境** | juicefs Secret 里是 `10.48.60.91:6382`（Redis）、`10.48.60.91:9010`（MinIO）和明文密钥；MinIO 清单在 ns `infra`，现网在 ns `kubeflow` | 直接 apply 会指向不存在的地址；`MINIO_HOST='minio.kubeflow:9000'` 也要同步改 |

**这四条卡的是"能不能起来"，与盘大小无关。** 落地顺序：

1. 给节点打 `pvrole` 标签（3 台×2 块盘，或 6 台×1 块）
2. 建 `local-minio` StorageClass（清单现成：`cluster/storage-class-minio.yaml`）
3. **按真实物理盘重写 6 个 PV 的容量**（清单里是模板值 2000Gi——测试环境不重要，生产按实际盘定）
4. 部署分布式 MinIO，把 `MINIO_HOST` 指向新 Service
5. 装 JuiceFS CSI，Secret 重新指向我们的 MinIO / Redis
6. 用 JuiceFS 版 PV/PVC 逐个替换 hostPath 版

> **容量在测试环境不是约束**（已确认非生产环境）。但生产要单独算一次：现状是"15 个 PV 声明合计 5212Gi，落在同一块盘上"，改成分布式后容量必须按真实物理盘重算，并去掉超卖。

#### ⚠️ 新增的单点：JuiceFS 的元数据引擎

JuiceFS 把**文件元数据放在 Redis 里**（`metaurl`）。而集群现有 Redis 是 **emptyDir、无持久化**，同时还兼职 Celery broker + 缓存 + DB 迁移锁。

**把 JuiceFS 元数据放进这个 Redis，等于工作区文件系统的元数据随时可能整体丢失**——数据块还在 MinIO 里，但"文件在哪"那张表没了。所以上 JuiceFS 之前，**必须先有一个持久化、最好 HA 的 Redis，且与 Celery 那个分开**。

### 4.5 顺带发现的三处既有缺陷（建议搭车修掉）

盘点存储时发现三个**和"迁 MinIO"无关、但同样是存储问题**的既有缺陷，都不大，建议在阶段一一起处理：

**缺陷 1：`DATASET_SAVEPATH` 在 K8s 下指向一个没有挂载的路径**

| 环境 | 值 | 实际挂载情况 |
|---|---|---|
| Docker | `$WORKSPACE_HOST_PATH/datasets`（`install/docker/config.py:930-932` **覆盖**） | ✅ 在 bind mount 内 |
| **K8s（行内）** | `/dataset/`（`config.py:786`，**没有覆盖**） | ❌ **无任何卷挂载这个路径**——`deploy-backend.yaml` 只挂了 `/data/k8s/kubeflow` |

后果：**HDFS 取数据的落地目录在 K8s 环境下是容器临时目录**，pod 一重启数据就没。这是两个 config 副本漂移造成的（docker 那份补了覆盖，k8s 这份没有）。修法：把 k8s 的 `DATASET_SAVEPATH` 改成 `$WORKSPACE_HOST_PATH/datasets`，与 docker 对齐。

**缺陷 2："保存镜像"不包含 notebook 文件**

`notebook-commit-*` pod 只 commit **容器 rootfs**（`async_task.py:59-89`），而 `/mnt` 是挂载卷、不在 rootfs 里。所以**用户点"保存镜像"保存的只是环境，不是代码和数据**——代码数据只存在于 NFS。这不是 bug（设计如此），但**是用户预期的常见误解**，而且它意味着：**只要 NFS 没了，用户的东西就真没了**，没有第二份。

**缺陷 3：数据集保存时静默丢弃路径**

`view_dataset.py:302-311` 的 `pre_add` 校验每条 path 是否在本地静态树里存在（`os.path.join('/home/myapp/myapp/static/', path)`），**不存在就静默丢掉**。用户填了一堆路径、点保存、只留下存在的那些，**没有任何提示**。这个是体验问题，但会造成"我明明登记了"的困惑。

### 4.6 三个方案

| 方案 | 做什么 | 解决单点？ | 评价 |
|---|---|---|---|
| **方案 A · 分布式 MinIO + JuiceFS（推荐）** | 6 节点分布式 MinIO 做对象底座，JuiceFS CSI 在其上提供 POSIX，逐个替换现有 hostPath PV | ✅ 全部 | **推荐**——清单齐备、PV 同名替换、应用层零改动 |
| **方案 B · 只做分布式 MinIO** | 6 节点分布式 MinIO，但 Jupyter 工作区不进 MinIO，继续放在"本地盘 + NFS 导出"上 | ⚠️ 一半 | 分布式 MinIO **自己不是单点**（多节点 + 纠删码，可容节点故障）；但它只接得住对象语义的数据。工作区是 POSIX 语义，进不去 → 工作区仍是单点 |
| **方案 C · Ceph 统一存储** | Ceph 同时提供块 / 对象 / POSIX | ✅ 全部 | 架构最全，但对小团队偏重，且仓库里没有对应清单 |

**建议方案 A。**

理由：它是**唯一一个既解决单点、又几乎不动应用代码**的方案——JuiceFS 版 PV 与现有 PV 同名，`subdir` 与现有路径对齐（`kubeflow/pipeline/workspace`）。业务代码里那些 `/mnt/...`、`/data/k8s/...` 硬编码路径**都不用动**。

#### ⚠️ 澄清：方案 B 的问题不是"MinIO 还是单点"

容易误读，单独说清：

**分布式 MinIO 本身就是多节点、有冗余的。** 它承载的那部分数据（Argo artifact、迁进去的数据集/模型/归档）确实是高可用了——这一点方案 B 就已经解决了，加节点不是问题。

**方案 B 的问题是覆盖面，不是节点数**：Jupyter 工作区是 **POSIX 语义**——JupyterLab 会实时随机写 `.ipynb`、建 conda 环境、clone git 仓库、用文件锁和 mmap。对象存储是 **API 语义**（GET/PUT 对象），装不下这类负载。**这是接口模型的问题，加多少节点都不行。**

所以只做分布式 MinIO 的话，工作区得继续留在某个共享文件系统上；如果那个文件系统还是现状的"本地盘 + NFS 导出"，单点就还在。

**JuiceFS 就是补这一层的**：它在分布式 MinIO 之上提供标准 POSIX 文件系统（自带元数据引擎和自己的块格式，不是 s3fs 那种简单封装），工作区放进去即可享受同一套冗余。

> **怎么选**：如果评估下来"工作区可以接受单点"——比如代码随时能从 git 重建、工作区只是临时环境——那**只做分布式 MinIO 就够了**，不必上 JuiceFS。反之，工作区里存了不可再生的成果，就该走方案 A。

**但方案 A 不等于"改配置就行"**：`MINIO_HOST`、JuiceFS Secret、StorageClass、节点标签都要改（见 4.4 的 6 步落地顺序）。

配套动作（**不能只动 MinIO 一个 PV**）：
1. **持久化 Redis**（给 JuiceFS 元数据用，与 Celery 那个分开）
2. NFS 导出规则收紧，去掉 `no_root_squash` 和 `*`
3. MinIO / JuiceFS 凭证从 manifest 里移出（现在是明文硬编码）
4. 生产环境单独重算容量，去掉超卖
5. **按与智算平台合并的要求预留接口**（见 `产品交付物/PRD-通用小模型平台.md` 8.2）

> ℹ️ **MySQL 不在此列**：数据库使用**行内托管的 TDMysql 服务**，**不由我们维护**，备份与高可用由行内 DBA 负责。

### 4.7 迁移风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **MinIO 迁移后仍是单点** | 单副本 + RWO PVC | 要么改分布式 MinIO，要么接受它只是"换了个位置" |
| 迁移期间停机 | 15 个 PV 全指向同一路径，无法灰度 | 规划停机窗口；当前无真实业务数据，窗口成本低 |
| `STORE_TYPE` 路径是死代码 | 一改配置就抛异常 | 先补存储抽象层，再接 MinIO |
| 数据集备份任务 | 备份逻辑走 worker + 文件系统拷贝 | 需要一起改，否则备份会备份到 NFS 上 |
| **改造 S3 抽象层的面很大**（P3 可选时才涉及） | 不只是搬数据：**数据集连上传接口都还没有**（用户是在 Jupyter 里传到 NFS 再登记路径）、notebook 的 `/mnt` 约定、模型部署时的 `cp`、流水线步骤间的路径约定——四类消费方都要改 | 立项时按"改造四个子系统"估算，**不要按"改配置"估算** |

## 五、诉求三：后端拆分成多 Pod

### 5.1 纠正一个前提：现在已经是 4 个 pod 了

| Deployment | 副本 | 角色 | 参考资料 |
|---|---|---|---|
| `kubeflow-dashboard` | 2 | Web/API（gunicorn 20 gevent worker，**兼做 DB bootstrap**） | `deploy-backend.yaml` |
| `kubeflow-dashboard-worker` | 2 | Celery worker（prefork -c 20） | `deploy-worker.yaml:110` |
| `kubeflow-dashboard-schedule` | 1 | celery beat，8 个定时任务 | `deploy-schedule.yaml:91` |
| `kubeflow-watch` | 1 | supervisord → 2 个 `Watch()` 循环 | `deploy-watch.yaml:95-96` |
| `kubeflow-dashboard-frontend` | 2 | nginx（**已经是独立镜像，独立部署**） | `deploy-frontend.yaml` |

所以问题不是"后端是一个大进程"，而是：**这 4 个 deployment 是同一个镜像、同一份 ConfigMap、同一次全量加载。**

> ### 📌 一个连带的好处：一期不交付低代码，`kubeflow-watch` 就不用部署
>
> `kubeflow-watch` 的唯一职责是**同步 Argo workflow 状态**——而 Argo 只服务流水线（属低代码编排，排二期）。所以一期不交付低代码的话：
>
> | 一期不用部署 | 少掉什么风险 |
> |---|---|
> | `kubeflow-watch` | 少一个**单点**（1 副本，挂了流水线状态不再更新） |
> | `workflow-controller` | 少一个组件 |
> | beat 里 4 个纯流水线的定时任务 | 少 4 个空转任务（其中 `task.watch_gpu` 在本环境纯空跑） |
>
> **这让一期实际要管的组件从 4 个后端降到 3 个**，也让阶段五的拆分少一块拼图。**组件清单保留不删**，二期随低代码一起启用。

### 5.2 迭代慢的真正原因（四条，都不是"没拆微服务"）

**原因一：改任何一处代码，4 个 deployment 全部要重启。**
镜像只有一个（`192.168.11.12/cube-studio/kubeflow-dashboard`），`build_backend.sh` 构建后 `kubectl set image` 更新 **4 个** deployment。改 `view_dataset.py` 的一行，worker/beat/watch 也一起滚。

**原因二：web pod 重启时还要跑一整套 DB 流程。**
`entrypoint.sh` 在起 gunicorn 之前顺序执行：建软链 → `create_db.py` → `db upgrade`（Redis 锁）→ `fab create-admin` → `myapp init` → `db.create_all()` → `check_tables.py`（`entrypoint.sh:22-80`）。其中 `check_tables.py` 在表不全时 **`exit(1)`**——**重启可能直接变成 CrashLoop**。

**原因三：每个角色都加载了全部 39 个 view。**
`myapp/__init__.py:392` 无条件执行 `from myapp import views`，`views/__init__.py` 导入约 30 个模块，每个模块在 **import 时** 调用 `add_view`/`add_api`（全仓 48 处）。**全仓搜 `STAGE` 在 Python 侧 0 命中——没有任何环境/角色判断。** 于是 worker、beat、连 `watch_workflow.py`（`watch_workflow.py:14` 就 `from myapp import app`）都要付出完整 Web 栈的加载代价，包括 `utils/core.py:4` 的 pandas、`:35` 的 numpy、FAB 模板栈、以及 `AppBuilder(update_perms=True)` 的 DB 写入。

**原因四（隐藏的硬耦合）：worker 依赖 view 层。**
`schedules.py:32` 直接 `import` `view_pipeline.run_pipeline`；`async_task.py:21,254,289` 导入 view 类，并在 `:235-236,:269` **在任务里实例化 `_ModelView_base()` 对象**。所以**不能简单地"把 views 从 worker 里摘掉"**——得先把业务逻辑从 view 里抽出来。

### 5.3 三个层次的拆分（成本递增，建议做到 L2 为止）

| 层次 | 做什么 | 收益 | 成本 | 建议 |
|---|---|---|---|---|
| **L1 · 角色化加载** | `myapp/__init__.py` 改为 `create_app(role="web"\|"worker"\|"beat"\|"watch")`，非 web 角色不加载 views | worker/beat/watch 启动变快、内存下降；可以单独重启某个角色 | 中（要处理原因四的耦合） | ✅ **做** |
| **L1.5 · 迁移外移**（低成本切入点） | 把 `entrypoint.sh:22-64` 的 DB 迁移拆到一个独立 `Job`/initContainer（复用现有 Redis 锁） | web pod 重启**直接起 gunicorn**，不再有 CrashLoop 风险 | **低** | ✅ **先做这个** |
| **L2 · 独立镜像 + 任务分队列** | 加 `task_routes` + 每功能一个队列，每个功能一个 worker Deployment | 改一个功能只滚一个 pod ← **这就是你想要的"迭代不用全重启"** | 中高 | ✅ **做** |
| **L3 · 服务化** | 抽出 service 层，解除 view ↔ task 循环依赖，按功能独立服务 | 最彻底 | 高 | ⏸ **已排入后续版本（阶段五），非否决** |

> L2 的技术前提已经具备：**当前全仓没有任何 `task_routes`/`task_queues`**，所有任务挤在一个默认队列里（`config.py:418-420`，且 `task.make_timerun_config` 每 5 分钟的任务和长任务抢同一个池子）。加路由是纯增量改动，不动现有逻辑。

> ### 📌 术语对齐（2026-09-24）：官方计划说的"微服务"= 本文的 **L2**，不是 L3
>
> 官方计划的说法是：**"一些模块以 pod 形式起来，这样上线迭代可以按模块更新镜像，而不用动主后端"**。
> 这**正是 L2**——按模块拆 pod + 独立镜像 + 单独滚动。
>
> **所以 L2 与官方计划没有冲突，而且它就是 V1.0 的核心工作。**
> ⚠️ 注意：**L2 与 L3 不是一回事**——把两者笼统说成"微服务"，会得出"与官方计划冲突"的错误结论。
>
> 澄清后的对应关系：
>
> | 层次 | 是什么 | 谁在做 |
> |---|---|---|
> | L1 角色化加载 | 拆出来的模块 pod 不该加载全部 39 个 view | 官方未明确提，但**是 L2 的伴生项** |
> | **L2 按模块拆 pod + 独立镜像** | 改一个模块只滚一个 pod | ✅ **官方 V1.0（阶段三）的核心工作** |
> | L3 服务化（抽 service 层、独立服务） | 真微服务 | ⏸ 不在官方计划内，仍建议后置 |
>
> **L3 与 L2 的区别**：L2 是"同一个镜像工厂产出多个可独立升级的 pod"；L3 是"业务逻辑彻底从 view 层剥离、
> 模块之间通过接口而非函数调用通信"。**官方要的是前者，本文档建议后置的是后者。**

**为什么 L3 排到阶段五、而不是现在做**：真正的微服务要先把 `view_pipeline`/`view_notebook` 等里的业务逻辑抽成 service 模块（这正是 `codebase-audit-and-refactoring-plan.md` 第二阶段的内容），工作量大、风险高，而且**在功能还没砍完之前做等于白做**。另外团队 7 人维护真微服务的成本偏高，**建议阶段五的形态是"模块化单体 + 关键路径独立部署"，而非一步到位。**

> ⚠️ **但 L3 虽然后置，有一个动作要提前**：**把业务逻辑从 view 层抽出（解除上面"原因四"的耦合）是 L2 的前置条件**——当前 `schedules.py:32`、`async_task.py:235-236` 直接依赖 view 层。所以这个拆分动作应该在**阶段三就做掉**，别等到阶段五。

### 5.4 一个必须知道的部署地雷

`deploy-backend.yaml:111-112` 里 `STAGE` 的值是字面量 `$(STAGE)`，**只有在 overlay 下才解析得开**（`overlays/kustomization.yml:35-42` 的 kustomize `vars`）。直接 apply `base/` 会得到 `STAGE=$(STAGE)` → entrypoint 走到 `myapp --help` → 容器直接退出。**这 4 个 pod 的拓扑只在 overlay 下成立。** 做拆分改造时不要绕过 overlay。

### 6.2 路线图

**阶段一 · 止血（1-2 个月）— 目标：数据不会丢**

按 4.4 的 6 步落地「分布式 MinIO + JuiceFS」：

- 给节点打 `pvrole` 标签 + 建 `local-minio` StorageClass（分布式 MinIO 清单的两个硬前置）
- 按真实物理盘重写 6 个 PV 容量，部署 6 节点分布式 MinIO，`MINIO_HOST` 指向新 Service
- 部署**持久化 Redis**（JuiceFS 元数据专用，与 Celery 的分开）
- 装 JuiceFS CSI，Secret 重新指向我们的 MinIO / Redis
- 用 JuiceFS 版 PV/PVC **逐个替换** hostPath 版（PV 同名，业务代码不用动）
- 拿到智算平台侧的工期节点，确认合并形态与接口预留要求
- NFS 权限收紧、凭证移出 manifest
- 搭车修掉 4.5 的三处既有缺陷（`DATASET_SAVEPATH` 漂移优先，它现在是真实数据丢失）
- 做完这条线，**"数据安全"才算闭环**——对象数据和 POSIX 数据在同一套冗余上

**阶段二 · 正确性与瘦身（2-3 个月）— 目标：产品对、体量小**

- 隔离改项目级（复用同目录的 `项目隔离-实施计划.md`，补齐 3.4 列出的四个细节）
- 14 个模块**隐藏**（保留 seed、代码、部署清单，支持一键恢复——**不是清理**）
- 迁移从 entrypoint 外移（L1.5）
- **顺序很重要**：先收窄本期范围再拆，否则拆完还要再改一遍

**阶段三 · 交付效率（2-3 个月）— 目标：迭代不用全重启**

- 角色化加载（L1）
- 任务分队列 + 功能独立 worker Deployment（L2）
- 视效果决定是否投入 L3

**待定 · 存储业务层（按需）**

- 方案 A 落地后，数据集/模型已经在有冗余的存储上了，**不要为"看起来更云原生"再迁一次**。
- 只有当出现真实诉求——数据集需要跨集群共享、需要对象存储的对象级版本管理/SDK 直读——才补 `myapp/utils/store/` 抽象层走 S3 API（注意：这个模块目前不存在，是新建不是改配置）。
