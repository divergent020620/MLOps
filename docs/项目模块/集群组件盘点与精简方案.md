# 集群组件盘点 + 精简版（只留 6 个功能）取舍方案

> 盘点时间：2026-09-24　方式：Tabby MCP 直连 5 台服务器 + 仓库对照
> 结论先行：**真正在跑的只有 40 个 pod、8 个 namespace**；清单里有 5 个功能模块（pipeline/automl/aihub/logging/EFK）**根本没部署**，砍它们零成本。
> 真正的坑不在"砍哪些"，而在**存储**：所有 PV 都是 hostPath，指向 `/data/k8s`，而 `/data/k8s` 是软链到 **master1 用 NFS 导出的一个 100G 本地目录**。你现在跑的整个平台，持久化根就是这一块盘。

---

## 一、节点与存储真相

| 服务器 | IP | 角色 | 原生进程（不在 K8s 里） |
|---|---|---|---|
| 服务器1 | .11 | master1 | **NFS server**（导出 `/bdm/share_bdm`）、haproxy、buildkit |
| 服务器2 | .12 | master2 | **Harbor**（docker-compose，HTTP :80）、**Gitea**（:3000） |
| 服务器3 | .13 | master3 | 无 |
| 服务器4 | .14 | worker1 | 无 |
| 服务器5 | .15 | worker2 | **MySQL 8.0.24 裸金属单实例**（`/usr/local/mysql/bin/mysqld`，systemd unit `mysqld`，root/admin，`kubeflow` 库） |

**全集群无 GPU**（5 个节点的 `nvidia.com/gpu` 都是 `<none>`）。

### 存储链路（关键）

```
Pod 的 PVC
  └─ PV: hostPath /data/k8s/kubeflow/...
       └─ /data/k8s  →  软链  →  /bdm/share_bdm
                                   └─ master1 本地 LV（100G，已用 56G，剩 45G）
                                       └─ NFS 导出 * (rw, no_root_squash, async)
                                           └─ 5 台机器全部挂载
```

- **集群里一个 StorageClass 都没有**，15 个 PV 全是 `storageClassName: ""` 的 hostPath。
- 15 个 PV 声称加起来 **5212Gi**（10 个各 500Gi + 2 个 100Gi + 1 个 10Gi + 2 个 1Gi），底下却是**同一块 100G、只剩 45G 的盘** → 相当于物理盘的 **52 倍**。
- 这就是你说的"不想要的 NFS 单点 + 没有备份"。它不是规划中的方案，它**已经是既成事实的根**。
- `no_root_squash` + `*` 任意主机可挂，安全上也是敞开的。

## 三、四个后端镜像到底谁干什么

**镜像其实只有 2 个**，4 个"后端"是**同一个 `kubeflow-dashboard` 镜像 + 不同 command**：

| Deployment | 副本 | command | 职责 | 挂载 |
|---|---|---|---|---|
| `kubeflow-dashboard`（backend） | **2** | `bash /entrypoint.sh`（STAGE=prod） | **唯一对外 HTTP 服务**。Flask+FAB+gunicorn；**同时兼职 bootstrap** | kubeconfig、`infra-kubeflow` PVC |
| `kubeflow-dashboard-frontend` | **2** | nginx | SPA + 反向代理 | nginx configmap |
| `kubeflow-dashboard-schedule` | **1** | `celery beat` | 定时器 | kubeconfig |
| `kubeflow-dashboard-worker` | **2** | `celery worker --pool=prefork -Ofair -c 20` | 异步任务执行器 | kubeconfig、`infra-kubeflow` PVC |
| `kubeflow-watch` | **1** | `supervisord` → `watch_workflow.py` | Argo workflow/pod 状态监听回写 | kubeconfig |

### 三个要点

1. **backend 的 entrypoint 不只是起服务**，它顺序做：建软链 → `create_db.py` → `db upgrade`（**用 Redis 锁 `cube:db-upgrade-lock` 抢，只有 1 个副本真正执行**）→ `fab create-admin` → **`myapp init`（灌初始数据，`|| true` 吞错）**。所以：**砍功能后必须同时砍 `myapp init` 的初始数据**，否则重启一次就灌回来。

2. **schedule 和 watch 都是单副本 = 各自一个单点**。schedule 挂了定时任务全停；watch 挂了流水线状态不再更新。watch 的 **16 次重启是设计如此**（liveness 探针里写了 `if [ $hour -eq 03 ]; then exit 1; fi`，每天 03:00 自杀回收进程），不是故障。

3. **只有 backend 和 worker 挂 PVC** → 只有它们碰文件系统（backend 提供静态文件下载，worker 做数据集备份/拷贝）。

### schedule 的 7 个定时任务（精简时逐个判断）

| 任务 | 频率 | 干什么 | 保留 6 功能时还需要吗 |
|---|---|---|---|
| `task.delete_workflow` | 每天 00:01 | 清过期 workflow CRD | ❌ 无流水线即空转 |
| `task.make_timerun_config` | **每 5 分钟** | 生成定时流水线运行配置 | ❌ 纯流水线 |
| `task.delete_old_data` | 每天 01:01 | 删 `/data/k8s/kubeflow/minio/mlpipeline` 旧数据 | ❌ 纯流水线 |
| `task.check_pipeline_run` | 每天 11:10 | 检查流水线运行时长、报警 | ❌ 纯流水线 |
| `task.delete_debug_docker` | 每天 23:30 | 删 debug pod | ✅ 建议留 |
| `task.watch_gpu` | 8–23 每 2 小时 | 推送 GPU 使用率 | ❌ **本集群无 GPU，纯空跑** |
| `task.watch_pod_utilization` | 每天 11:10 | 推送低负载 pod | ✅ 可选留 |
| `task.check_pod_terminating` | **每 10 分钟** | 清理卡在 Terminating 的 pod | ✅ **建议留，很有价值** |

> 已注释掉的：`delete_notebook`、`push_workspace_size`、`adjust_node_resource`。

## 四、只保留 6 个功能时：哪些必须留

保留清单：**基础登录注册 / 用户管理 / Jupyter / 推理服务 / 中间件服务 / 取数存数**

> 口径说明：「中间件服务」在平台里对应的是 **`service` 功能**（`myapp/init/init-service.json` 的 8 个模板：mysql-ui、redis-ui、mongo-express、neo4j、postgresql-ui、es、sd-webui、xinference），DB 里有 8 条记录。如果你的意思其实是"平台自己的中间件层"，结论一样——下面标"必须留"的一条都跑不掉。

### 一个都不能砍

| 组件 | 为什么 | 备注 |
|---|---|---|
| **MySQL**（**服务器5 裸金属**） | 用户/角色/项目/notebook/dataset/inference 全在里面 | ⚠️ 见下方「MySQL 的三个隐患」 |
| **Redis** | Celery broker + Flask cache + **db upgrade 锁**。砍了多副本启动迁移会打架 | ⚠️ emptyDir，无持久化 |
| **backend ×2 + frontend ×2** | 唯一入口 | — |
| **Istio**（istiod ×2 + gateway ×2） | 这 6 个功能里，**Jupyter、推理服务、中间件服务三个都靠 VirtualService 对外暴露** | 集群没装 Ingress Controller |
| **MetalLB** | 给 istio gateway 分 VIP；没它外部进不来 | — |
| **共享存储**（`/data/k8s` 那套） | notebook 的 `/mnt`、取数存数的 `/dataset`+`/global`、后端静态下载全指它 | ⚠️ 就是那个 NFS 根 |
| flannel / coredns / metrics-server / kube-* | K8s 自身 | — |

### 靠 istio 的地方（这是"能不能绕过 istio"的关键）

`create_istio_ingress` 被这几处调用：**推理服务**、**服务(中间件)**、**NNI**、**notebook**、资源清理。
里面有一句关键逻辑：

```python
host = host.split(":")[0]
if not host or core.checkip(host):
    return          # ← 传 IP 就跳过，不建 VirtualService
```

**所以平台自带一条降级路径**：把对外地址配成 IP，就不再建 VirtualService。但要走这条路，得先有个 Ingress Controller 或接受 NodePort 直连——`install/kubernetes/ingress.yaml` 那套 Ingress 对象**在集群里没有任何 controller 兜底**（`kubectl get ingress` 为空）。**结论：6 功能下 Istio 不建议砍，绕过成本高于收益。**

### ⚠️ MySQL 的三个隐患（它在服务器5 裸金属上）

1. **和业务负载抢同一台机器。** 服务器5 同时是 K8s worker 节点（跑着 `admin-a855`、`admin-jupyter` 两个 notebook）。节点一挂 / 一 drain，数据库跟业务一起没。
2. **它是单点，没有副本、没有主从。** 整库的落盘就是 `/usr/local/mysql` 下面的数据目录，没看到备份任务。
3. **仓库里的 K8s MySQL 清单和实际部署对不上。** `install/kubernetes/mysql/deploy.yaml` 用 `nodeSelector: mysql=true`，而 **`mysql=true` 这个标签打在 3 台 master 上，服务器5 根本没有**。说明 K8s 那套 MySQL 是被 `start.sh --mysql-host` 跳过、手工裸机装的。`infra` namespace 里还留着 `mysql-configmap`（含 `mysqld.cnf` + `init.sql`）说明当年 apply 过一半。

> 这三条合起来是本次盘点里**风险最高的单点**——比那块 NFS 盘还高：存储盘挂了数据还在别的机器上，MySQL 挂了整站不可登录。

## 五、可以砍的组件 / 可以绕过的模块

### A. 建议直接砍（低风险）

| 组件 | 理由 | 代价 / 注意 |
|---|---|---|
| **dcgm-exporter** | **本集群无 GPU，DS 根本没起 pod** | 无 |
| **`kubeflow-dashboard-schedule` 的 4 个任务** | 3 个纯流水线 + 1 个 GPU（没 GPU）。**别整条砍**，改 config 即可 | 保留 delete_debug_docker / check_pod_terminating / watch_pod_utilization |
| **`labelstudio` VirtualService** | 没有对应 pod，残留 | 无 |
| **`default` namespace 的 0 副本 Deployment** | 残留 | 无 |
| **`admin-hdfs` notebook + HDFS 代码**（`view_hdfs.py`、`hdfs_tasks.py`、`notebook-hdfs-build/`） | 集群里没有任何 HDFS | 无 |
| **Gitea（master2:3000）** | 服务"代码仓库"功能，不在保留清单 | ⚠️ 有人拿它存代码就别停，先问 |
| **`logging` / `service` / `pipeline` / `automl` / `aihub` namespace** | 空着，砍了没影响 | 保留也没成本 |

### B. 建议砍，但要先确认（中风险）

| 组件 | 理由 | 必须先确认 |
|---|---|---|
| **`kubeflow-watch`** | 唯一职责是同步 Argo workflow 状态。**没流水线它就没活干** | 是否还有人在用流水线（DB 里 `run`=0，看起来是空的） |
| **`minio`（kubeflow ns）** | 只给 Argo 存 artifact。**取数存数的真实后端不是 MinIO**（见下） | 是否有存量 workflow 依赖它；`config.py` 的 `MINIO_HOST` 要一起清 |
| **`workflow-controller` + Argo CRD** | 流水线被砍后完全无用 | 同上 |
| **`training-operator`** | 只管分布式训练，不在保留清单 | 砍了所有 `tfjob`/`pytorchjob`/`mpijob`/`paddlejob`/`mxnet` 模板全废（DB 里有这些模板） |
| **`volcano`** | 只服务 `vcjob` 分布式调度 | 同上 |
| **`kubernetes-dashboard-user1`** | 用户级 K8s 控制台 | 保留清单没提；`cluster` 那个建议留作排障入口 |
| **prometheus**（保留 grafana + node-exporter） | 保留清单没提监控；但 **Grafana 是推理服务页面的跳转目标**（`GRAFANA_SERVICE_PATH`），删了会有死链 | 建议降配而非删除：调小 prometheus 的 PVC / 保留期 |

### C. 可以绕过的**代码模块**（不改部署，只收功能面）

DB 里这些表有数据，但都不在保留清单：`aihub`(**501 条**！)、`nni`、`etl_pipeline`、`metadata_table`(**27**)、`chat`(**12**)、`model`、`repository`、`sqlab_query`、`announcement`、`docker`。

对应可下线的 view：`view_nni.py`、`view_etl_pipeline*.py`、`view_metadata*.py`、`view_dimension.py`、`view_chat.py`、`view_train_model.py`、`view_aihub.py`、`view_sqllab.py`、`view_docker.py`、`view_announcement.py`、`view_hdfs.py`、`view_workflow.py`、`view_runhistory.py`、`view_total_resource.py`。

**做法**：不只是藏菜单，还要从 `myapp/cli.py` 的 `myapp init` 里摘掉对应的 seed 数据，否则每次后端重启又被灌回来。

### D. 有个功能性坑：`mysql-ui` 是坏的

`init-service.json` 里 `mysql-ui` 指向 `PMA_HOST=mysql-service.infra:3306`，但**全集群没有 `mysql-service` 这个 Service**（MySQL 是 worker2 裸机进程，不在 K8s 里）。所以 8 个中间件模板里 **`redis-ui` 能用、`mysql-ui` 一开就报错**。

修法二选一：给 worker2 的 MySQL 建一个 ExternalName/Endpoints Service 叫 `mysql-service`；或者把这个模板下架。

## 六、结论：给你一张选择题

| 你的问题 | 答案 |
|---|---|
| 哪些中间件是不需要的？ | MinIO、Argo（workflow-controller/watch/schedule 的流水线部分）、training-operator、volcano、dcgm-exporter。**EFK/Kafka/Alluxio/JuiceFS/Ceph 本来就没装。** |
| 哪些模块可以绕过？ | NNI、ETL、元数据管理、SQLLab、在线构建镜像、AIHub、chat、模型仓库、公告、HDFS、代码仓库——共 14 个 view，配合摘掉 `myapp init` 的 seed。 |
| 哪些一个都不能动？ | MySQL、Redis、backend、frontend、Istio+MetalLB、共享存储、K8s 基础件。 |
| 最该先处理的是什么？ | **不是砍组件，是存储。** 现在 15 个 PV 超卖在同一块剩 45G 的 NFS 盘上，`no_root_squash` + 任意主机可挂、无备份、无快照。这才是真正的单点。 |
