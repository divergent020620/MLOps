01请求怎么进来的

你在浏览器里敲一个地址，流量要经过几道手才到后端。

部署在 istio-system 和 metallb-system 两个 namespace，跑在 master1 / master3 / worker2

Pod / 对象副本它是干什么的（说人话）在哪
metallb speaker5 给内网"借"一个真实 IP 当负载均衡。没有云厂商的 LB，MetalLB 就让每台机器用 ARP 广播喊"192.168.11.201 在我这儿"，把流量吸引过来。每台机器一个。 全部 5 台
metallb controller1 IP 分配员。谁申请 LoadBalancer 类型的 Service，它就从地址池里发一个 IP，并告诉 speaker 们去广播。 worker2
istio-ingressgateway2 平台的唯一大门。外部流量全从这里进来，再按域名和路径分发给内部的服务。就是它占用了 VIP 192.168.11.201。 master1 / master3
istiod2 Istio 的大脑。把 VirtualService 这些"路由规则"翻译成 Envoy 能懂的配置，下发到网关上。
※ 本集群所有 namespace 都标了 istio-injection: disabled，所以它只当网关的控制面，不做服务网格（不给业务 Pod 塞 sidecar）。		 master1 / master3
Gateway （配置对象，不是 pod）2 规定"门开在哪"。kubeflow-gateway 监听 80，kubeflow-gateway-8080 监听 8080，host 都是 *（什么域名都接）。 kubeflow ns

完整的进门路径

浏览器 → 192.168.11.201:80（MetalLB 借来的 VIP）→ istio-ingressgateway → 按 VirtualService 规则分流 → 后端 / notebook / Grafana / K8s Dashboard

目前挂在网关后面的 VirtualService 共 11 个：平台后端、6 个 notebook、2 个 K8s Dashboard、Grafana，加一个没有对应 Pod 的 labelstudio。

⚠️ 这个模块的问题
  • 没有 Ingress Controller。install/kubernetes/ingress.yaml 里那几个 Kubernetes 原生 Ingress 对象，集群里没有任何 controller 去实现它们（kubectl get ingress 是空的）。这份配置是死的，别以为它生效了。
  • labelstudio VirtualService 是残留：路由指向一个不存在的服务，属于删了没影响的垃圾配置。
  • VIP 是 L2 广播方式。MetalLB 在 L2 模式下，同一时刻只有一个节点在响应 ARP。所以虽然 istio-ingressgateway 有 2 个副本，入口带宽实际由一台机器承担，节点故障时 VIP 要漂移几秒。
  • MetalLB后面会被haproxy替代，目前只是一个暂时状态，最后用haproxy指向127.0.0.1来完成集群的HA

任务什么时候跑干什么

⚠️ 这个模块的问题
  • schedule 和 watch 都是单副本，各自是单点。schedule 挂了 → 所有定时任务停摆（包括"清理卡死的 Pod"）；watch 挂了 → 流水线进度不再更新。只有 backend 和 worker 是 2 副本。
  • backend 兼着"数据库迁移"这件事。它靠 Redis 加锁保证多副本里只有 1 个真正执行迁移。好处是防止并发迁移打架，坏处是如果 Redis 挂了，新 Pod 启动时会卡在"抢锁"环节（代码里是重试 30 次、每次 2 秒，60 秒后放弃继续）。
  • 每次重启都会重灌初始数据（myapp init，后面跟了 || true 吞掉错误）。这带来一个副作用：以后要下线任何功能，光删数据没用，得同时改掉 init 的数据源，否则重启一次就全回来了。
  • 前端日志没挂出来。nginx 的 access_log / error_log 写在容器内的 /data/log/nginx/，但 Pod 只挂了一个 nginx 配置文件，这个目录在宿主机上也不存在 → 前端访问日志实际是丢的，Pod 一重建就没了。
  • watch 每天 03:00 会自己重启一次（它的 liveness 探针里写了 if [ $hour -eq 03 ]; then exit 1; fi）。这是设计如此不是故障，但意味着每天凌晨有约一分钟窗口它不工作。

03数据存在哪

平台有四种"存东西"的地方，各管一摊。这一块是当前风险最集中的模块。

共享盘在 服务器1　·　MinIO + Redis 在 kubeflow / infra ns　·　MySQL 在 服务器5 裸金属

存储管什么数据它是干什么的（说人话）在哪
MySQL平台所有元数据 平台的账本。用户、角色、项目、notebook 记录、数据集记录、推理服务配置……全在 kubeflow 库里。表结构有 35 张。 服务器5 裸机
共享盘（NFS）文件本体 真正的文件都放这儿。notebook 里的 /mnt/<用户名>、数据集目录、模型文件、后端做文件下载的源目录，全指向它。 服务器1 导出
minioArgo 的中间产物 S3 对象存储。目前只服务 Argo——任务流每一步之间要传递文件，就临时扔这儿。 kubeflow ns / master3
redis队列 + 缓存 + 锁 三个身份合一：① 异步任务的消息队列（backend 扔、worker 取）② 页面缓存 ③ 数据库迁移的分布式锁。 infra ns / master3

共享盘是怎么回事（重点）

Pod 拿到的是一个"持久卷"，看上去是本地目录 /data/k8s/…。但一路追下去：

PVC → PV（hostPath，全集群没有一个 StorageClass）
  → /data/k8s/… → 这是个软链 → /bdm/share_bdm
    → 服务器1 用 NFS 导出这个目录，5 台机器统统挂载
      → 最终落盘：服务器1 本地盘 100G，已用 56G，剩 45G

换句话说：整个平台唯一的持久化落点，是服务器1 上的一块盘。

🔴 这个模块问题最多，按严重程度排
  • 共享盘超卖约 52 倍。15 个 PV 声称加起来 5212Gi（10 个各写 500Gi），底下却是同一块只剩 45G 的盘。任何一个 notebook 写满，全平台一起停。
  • 共享盘权限敞开。导出配置是 /bdm/share_bdm *(rw,no_root_squash,async) —— * 意味着任意主机都能挂，no_root_squash 意味着挂上来的客户端 root 就是真 root。
  • 共享盘没有快照、没有备份。而且它是 NFS，你之前明确不想要的那种"单点 + 无备份"的东西——它早就是整个平台的地基了。
  • Redis 没有持久化。用的是 emptyDir（临时目录），Pod 一重启：在跑的异步任务丢失、页面缓存清空。仓库里其实有现成的 Redis PVC 配置，但实际部署没用上。（对"迁移锁"影响不大，那是个短时租约。）
  • 仓库清单和实装对不上。install/kubernetes/mysql/deploy.yaml 写的是 nodeSelector: mysql=true，可这个标签打在三台 master 上，服务器5 根本没有 → 说明 K8s 那套 MySQL 当年是被 start.sh --mysql-host 跳过、手工装的。infra ns 里还留着 mysql-configmap 是当年的残迹。
  • MinIO 是单副本 + 单块 hostPath。Pod 挂了就没了。好消息是它只存 Argo 的中间产物，且那个目录目前是空的（说明任务流从没跑过）。后续要考虑使用MinIO来替代NFS

每个 notebook 是怎么起来的

平台会为它创建三样东西：一个 Pod（跑 jupyter lab，端口 3000）+ 一个 Service（给 Pod 一个集群内地址）+ 一个 VirtualService（把外部访问路由进来）。

挂载：/mnt/<用户名> → 共享盘里的个人工作目录　·　/mnt/datasets → 数据集目录（只读）

高代码路线怎么继续往下走：在 notebook 里训练完 → 点「保存镜像」→ 平台起一个 notebook-commit-xxx 的临时 Pod 把当前容器 commit + push 到 Harbor → worker 轮询最多 30 分钟确认结果，成功后把镜像名记回 notebook 记录 → 之后就能拿这个镜像去部署推理服务。

⚠️ 这个模块的问题
  • 「保存镜像」依赖 worker。check_notebook_commit 是跑在 worker 上的 celery 任务。这条依赖很隐蔽——只看"谁挂了存储卷"是看不出来的，因为 worker 也挂了，容易误判成"可以砍"。

05任务与任务流（低代码）

平台里有两个不同的功能容易混：「任务」是跑单个作业，「任务流」是把多个作业串成一张图（DAG）交给 Argo 调度。菜单里分别叫「任务」和「任务流」。

控制器在 kubeflow ns　·　任务流跑起来后 Pod 落在 pipeline ns（当前是空的）

Pod副本它是干什么的（说人话）在哪
workflow-controller1 任务流引擎（Argo Workflows）。你在页面上拖出来的那张图，编译成一个 Workflow 对象交给它，它负责按依赖顺序把每一步跑起来、失败重试、记录状态。每一步就是一个 Pod。
※ 注意：没部署 argo-server，所以没有 Argo 官方的那个 Web UI，只能从平台页面看。		 master1
training-operator1 分布式训练的"专用工单处理器"。认 TFJob / PyTorchJob / MPIJob / PaddleJob / MXJob / XGBoostJob 这几种 CRD，把它们翻译成一组 Pod（比如 1 个 master + N 个 worker）。 worker1
volcano-scheduler1 批调度器。负责"组调度"——一个分布式训练要 8 个 Pod，它保证要么 8 个一起排上，要么一个都不占，避免出现"占了 3 个卡在那儿干等"的僵局。 master1
volcano-controllers1 Volcano 的控制器。管理 vcjob 这个 CRD 的生命周期（创建、状态跟踪、清理），配合上面的 scheduler 工作。 master1

「任务」和「任务流」的区别

「任务」（view_task.py）：从 98 个作业模板里挑一个，填参数，直接建 K8s 资源。不走 Argo。

「任务流」（view_pipeline.py，菜单标题就是「任务流」）：拖一张 DAG，每个节点选一个作业模板 → 平台合成一个 Argo Workflow → 提交到 pipeline namespace → workflow-controller 执行 → kubeflow-watch 把状态写回数据库。

两者共用同一批作业模板，区别只在"单步"还是"多步编排"。

⚠️ 这个模块的问题
  • 零使用。库里 pipeline 表 4 条、workflow 表 0 条、run 表 0 条；集群里 0 个 Job、0 个 Workflow、0 个已结束的 Pod；MinIO 的产物目录 是空的。→ 这套东西装了 72 天，一次没跑过。
  • 那 4 条任务流是安装器自带的演示数据。名字 yolov8 / ml / deepseek / electric-bicycle，跟 myapp/init/init-pipeline.json 里的键一字不差，且全部创建于 2026-07-14 12:23:03~05（建集群那 3 秒内，myapp init 灌进去的）。
  • 没部署 argo-server → 平台以外没有 Argo 界面，排查问题只能靠 kubectl 或平台页面。
  • watch_gpu 这个定时任务在空转。本集群 5 个节点都没有 GPU（nvidia.com/gpu 全是 <none>），但它还是每 2 小时跑一次推 GPU 使用率。

06推理服务与中间件服务

这是平台把"训练成果"变成一个可访问的在线服务的地方，也是"一键起个 MySQL 管理界面"这类工具的地方。

都部署在 service namespace（当前 0 个 Pod）

功能它是干什么的（说人话）背后建了什么
推理服务 把镜像变成能访问的 API。你选一个镜像（比如 notebook 保存出来的那个），填模型路径、端口、资源，平台帮你部署起来并给它一个访问地址。 普通 Deployment + 普通 Service + VirtualService（Istio 暴露）+ 可选的 HPA（自动扩缩容）。不碰 Argo。还支持金丝雀发布、影子流量（靠改 VirtualService 权重做滚动升级）。

⚠️ 这个模块的问题
  • 推理服务一条都没真正在跑。数据库里有 5 条记录，但 service namespace 里一个 Pod 都没有，也没有对应的 VirtualService。其中 4 条是安装器灌的演示数据（mnist-202208011、resnet50-202208012/3/4，全部创建于 2026-07-14 12:23:05），只有 1 条 batch-202608241 是人建的（08-24）。
  • mysql-ui 模板是坏的。它指向 mysql-service.infra:3306，但全集群根本没有这个 Service（MySQL 是服务器5 上的裸机进程，不在 K8s 里）。一开就报错。

  • 过半模板需要额外准备才能用。8 个里只有 redis-ui 开箱即用，其余要么需要外部实例、要么需要模型文件、要么需要共享盘目录。

08集群地基

这些不是 Cube Studio 的东西，是 K8s 本身跑起来必需的。没有它们整台机器都不转。

主要在 kube-system 和 kube-flannel 两个 namespace

组件副本它是干什么的（说人话）
etcd3 整个集群的账本。所有 K8s 对象（Pod、Service、配置……）都存在这里。它是集群里最不能丢的东西。3 副本，多数派存活即可用。
kube-apiserver3 唯一的正门。所有人（包括 kubectl、平台后端）都只能通过它读写集群，它是唯一直接跟 etcd 说话的。
kube-controller-manager3 自动纠偏程序。不停对比"实际状态"和"你要的状态"，不一样就动手改。比如 Pod 挂了它负责重建。
kube-scheduler3 派活儿的。决定一个新 Pod 该放到哪台机器上（看资源够不够、标签对不对、亲和性满不满足）。
kube-proxy5 Service 的接线员。让"一个 Service 名"能对应到后台多个 Pod，并做流量转发。每台机器一个。
kube-flannel-ds5 跨机器的网络。让 A 机器上的 Pod 能直连 B 机器上的 Pod（CNI 插件）。每台机器一个。
coredns2 集群内的电话簿。服务之间互相访问用的域名（比如 minio.kubeflow）就是它解析的。
metrics-server1 资源数据源。给 kubectl top 和自动扩缩容（HPA）提供 CPU/内存数字。
kubernetes-dashboard-cluster1 管理员用的 K8s 原生控制台。平台菜单里的「K8s Dashboard」跳转的就是它。带一个 metrics-scraper 采集指标。
kubernetes-dashboard-user11 用户级的 K8s 控制台（权限受限版）。同样带一个 metrics-scraper。
⚠️ 这个模块的问题
  • 3 个 master 同时是控制面和负载节点。它们身上还跑着平台后端、Redis、监控、任务流控制器等等。虽然打了 node-role.kubernetes.io/control-plane 的污点通常能隔离普通业务 Pod，但平台自己的组件是特意调度上去的（靠 kubeflow-dashboard=true 等标签）。结果是控制面的稳定性和平台组件的稳定性绑在一起了。
  • 两个 K8s Dashboard 的权限都很大，而且都通过 Istio 网关暴露在同一个 VIP 后面，靠路径区分。建议至少把 user1 那个收一收。

09镜像仓库（在 K8s 之外）

这一块不在 K8s 里，所以 kubectl get pods 看不到它，之前几轮的清单里也没有它。但它是整个平台的供应链起点。

跑在 服务器2（192.168.11.12），用 docker-compose 部署，不是 K8s 工作负载

服务它是干什么的在哪
Harbor 私有镜像仓库。所有镜像都从 192.168.11.12/cube-studio/* 拉。由 8 个容器组成：harbor-core（主服务）、harbor-portal（界面）、harbor-jobservice、registry（真正存镜像的）、registryctl、harbor-db（元数据库）、redis、nginx（入口）。 服务器2 :80

⚠️ 这个模块的问题
  • Harbor 是单点，还没有备份。它跑在一台机器上（服务器2），用 docker-compose 编排，不在 K8s 里、不受监控、不会自动重建。systemctl is-active harbor 返回的是 inactive（因为没有 systemd unit）—— 意味着机器重启后 Harbor 不会自动起来，得手工 docker compose up。
  • 走的是 HTTP 明文。curl http://192.168.11.12/v2/ 返回 401（服务在，需要认证），但协议是 http 不是 https。镜像拉取和推送的内容在内网是明文的。
  • 它的元数据库 harbor-db 也在同一台机器上，和 registry 共命运。
  • Harbor 一挂，全平台的新部署都受影响（已有 Pod 不受影响，因为镜像已在本地），但「保存镜像」和新建 notebook/推理服务会直接失败。

A附录：StorageClass 速查

前面反复出现"全集群没有一个 StorageClass"。这一节讲清它是什么、为什么这里没有、以及为什么装了它也不解决根本问题。

相关模块：03 数据存储　·　10 清单里有、实际没装的

一句话：StorageClass 是「存储的模板」

它回答一个问题："有人要一块盘的时候，我该去哪儿拿、怎么造、按什么规格造？"

没有它，只能是管理员先手工造好盘，再等人来申请；有了它，用户提一张申请单，盘自动出现。

概念是什么类比数量关系
StorageClass怎么造（模板 / 规格）菜谱：「3 副本、SSD、可扩容」一对多
PVC用户的申请单点单：「按这个菜谱来 10G」一对一
PV造出来的那块盘端上来的那份菜一对一

注意：PVC 和 PV 是一一对应的，而 StorageClass 能造出无数块盘。

核心区别：静态供给 vs 动态供给

现状是「静态供给」——手工作坊：

# ① 管理员先登服务器，手工建目录 # mkdir /bdm/share_bdm/kubeflow/dataset # ② 再手工登记一个 PV —— 这一步就是"造盘" kind: PersistentVolume metadata: {name: jupyter-kubeflow-dataset} spec: capacity: {storage: 500Gi} # ← 随手填的数字，K8s 无法校验 storageClassName: "" # ← 空字符串 = 不用模板，只能手工配对 hostPath: {path: /data/k8s/kubeflow/dataset} # ③ 用户写 PVC，还得写 storageClassName: "" 才配得上

有 StorageClass 之后——自动化工厂：

kind: StorageClass metadata: {name: nas-light} provisioner: nfs.csi.k8s.io # ← 谁来"造盘"（关键就是它） parameters: server: 192.168.11.11 share: /bdm/share_bdm reclaimPolicy: Retain allowVolumeExpansion: true # ← 支持在线扩容 --- # 用户的申请单就只剩这么点 kind: PersistentVolumeClaim spec: storageClassName: nas-light # ← 只写这一行，PV 自动生成并绑定 resources: {requests: {storage: 10Gi}}

中间那个 provisioner 是关键——它是 CSI 驱动，收到 PVC 后真的去调后端接口造一块盘，造完自动建 PV 并绑定。本集群没装任何 CSI 驱动，所以 PV 全靠手工登记。

能力现在（hostPath）有 StorageClass 之后
容量约束❌ 那个 500Gi 纯粹是装饰，没人管✅ 按申请的大小真去造
在线扩容❌ 改 YAML 数字，盘不会变大✅ 改 PVC 的 size 就能扩（需 allowVolumeExpansion）
多档套餐❌ 只有一种✅ 可并存 fast-ssd / cheap-hdd / shared-nas，按业务挑
删 PVC 之后❌ 手工决定✅ reclaimPolicy: Delete/Retain 自动处理
调度时机❌ 无✅ volumeBindingMode: WaitForFirstConsumer（等 Pod 定好节点再造盘，避免造错地方）
配额❌ 无✅ 配合 ResourceQuota 限制"某团队最多申请多少存储"

为什么这里一个都没有 —— 一条因果链

Ceph / NFS-CSI / JuiceFS / Longhorn 全都没装 ↓ 没有任何 provisioner 可用 没有"存储模板"可写 → StorageClass 一个都建不出来 ↓ 只能人工划目录 + 手工登记 hostPath PV ↓ 手工填的容量数字没人校验（为省事都填 500Gi） ↓ 15 个 PV 声称 5212Gi，底下只剩 45G —— 超卖 52 倍

所以"没有 StorageClass"不是原因，是结果——它是"没装任何存储驱动"这件事最直观的症状。它和模块 10 里那份"没装清单"是同一件事的两面。

⚠️ 但要说句实话：装了 StorageClass 也解决不了根本问题
  • NFS 目录做不了硬配额。就算装了 NFS CSI，requests.storage 也只是"造目录时记个数"，目录写满了照样爆（除非 NFS 服务端支持 project quota）。要真限制住，得用块存储（Ceph RBD / 云盘那种）。超卖那 52 倍不会因为装了 SC 就消失。
  • 单点也不会变。StorageClass 只换了"谁来划目录"，底层还是服务器1 那一块盘、那一个 NFS 导出。
  • 一句话：StorageClass 能把「管理方式」变好，但变不了「物理上的单点」。要动物理层，还是得回到"到底用哪套存储后端"这个决策——也就是模块 10 里列的那几个候选（Ceph / JuiceFS / NFS-CSI / Longhorn）。
🔴 顺带一个比 StorageClass 更该担心的坑：静默数据分裂

现在这套 hostPath + 软链的方案，藏着一个不会报错的故障模式。worker 节点上的实际结构是：

/bdm ← 节点本地的 XFS 盘（真实存在，空的） └─ share_bdm/ ← NFS 挂载"覆盖"在这个子目录上 /data/k8s → 软链指向 /bdm/share_bdm

关键点：/bdm/share_bdm 底下本来就是一个本地目录，NFS 只是盖在它上面。于是有两种失败方式，都不会给你明确的错误提示：

  • ① 挂载时失败（服务器1 没起来、NFS 服务没启）→ /bdm/share_bdm 就露出底下那个本地空目录。Pod 能正常启动、不报任何错，但 notebook 里的 /mnt 是空的；往里面写的数据落在本地盘上，等 NFS 恢复后被挂载点盖住，等于凭空消失。
  • ② 挂载成功后服务器1 掉线 → 挂载参数里带了 hard（实测：hard,proto=tcp,timeo=600,retrans=2）→ IO 会永久阻塞而不是报错。表现是"notebook 突然卡死、日志里什么都没有"。
    （hard 的取舍是"宁可卡住也不丢数据"，但对使用者来说就是无声的挂起。）

建议：在这块盘上加一个"挂载点存活"的检查（判断 /bdm/share_bdm 是不是真的 NFS 文件系统，而不只是个目录），比单纯看容量水位更能提前发现问题。这和模块 07 里"监控数据也放在同一块盘上"是同一个盲区。
