## 0. 一句话概括骨架

```
5 个 K8s Deployment（同一镜像，靠 command 分叉）
        │
        ├─ kubeflow-dashboard   → bash /entrypoint.sh      → gunicorn → Flask
        ├─ kubeflow-dashboard-schedule → celery beat
        ├─ kubeflow-dashboard-worker   → celery worker
        ├─ kubeflow-watch       → supervisord → 两个 k8s watch 循环
        └─ kubeflow-dashboard-frontend → nginx（静态 + 反代）

后端三层：
   View 层（views/*.py）      每个业务模块 = Filter + Base + Api 三件套
        ↓ 调用
   K8s 层（utils/py/py_k8s.py） 一个 K8s 类，约 70 个方法；核心是三件套
        ↓ 写入
   Model 层（models/*.py）    SQLAlchemy 表对象 + 一堆"展示用"方法

回写路径两条（互补）：
   Celery beat 定时轮询（schedules.py）+ k8s watch 事件驱动（tools/watch_*.py）
```

## 1. 运行时拓扑：5 个 Deployment

全部来自 `install/kubernetes/cube/base/deploy-*.yaml`，**同一个后端镜像、同一份 ConfigMap，靠 `command` 分叉角色**：

| Deployment | replicas | 容器名 | command | 角色 |
|---|---|---|---|---|
| `kubeflow-dashboard` | 2 | `kubeflow-dashboard` | `bash /entrypoint.sh` | Web API |
| `kubeflow-dashboard-schedule` | 1 | `kubeflow-dashboard-schedule` | `celery --app=myapp.tasks.celery_app:celery_app beat` | 定时投递 |
| `kubeflow-dashboard-worker` | 2 | `kubeflow-dashboard-worker` | `celery ... worker --pool=prefork -Ofair -c 20` | 异步执行 |
| `kubeflow-watch` | 1 | `kubeflow-watch-workflow` | `supervisord -c /home/myapp/myapp/tools/supervisord.conf` | 事件监听 |
| `kubeflow-dashboard-frontend` | 2 | `kubeflow-dashboard-frontend` | （nginx `start.sh`） | 静态 + 反代 |

> ⚠️ `kubeflow-watch` 的容器名是 **`kubeflow-watch-workflow`**，不是 `kubeflow-dashboard`。
> 排查时 `kubectl logs deploy/kubeflow-watch -c kubeflow-watch-workflow`。

四个后端 Deployment **都挂同一个 ConfigMap** `kubeflow-dashboard-config`（`deploy-backend.yaml:150`、`deploy-schedule.yaml:130`、`deploy-worker.yaml:149`、`deploy-watch.yaml:128`）。
这意味着：**改错一份 config.py，四个角色一起崩**。

## 3. 配置体系：为什么 `config.py` 有四个副本

这是本仓库**最容易踩坑、也最值得先搞懂**的一环。

### 3.1 加载机制

```
镜像里 /home/myapp/myapp/config.py  ← 0 字节（空文件）
        ↑ 被 subPath 挂载「覆盖」
ConfigMap kubeflow-dashboard-config 的 config.py 键
        ↓
CONFIG_MODULE = os.environ.get("MYAPP_CONFIG", "myapp.config")
app.config.from_object("myapp.config")
```

`MYAPP_CONFIG` **在 K8s manifest 里从未设置** → 恒为默认值 `myapp.config` →
实际生效的就是"被 ConfigMap 覆盖后的 `/home/myapp/myapp/config.py`"。

同一个套路在本地 docker-compose 里也有一份（`install/docker/docker-compose.yml:68`）：

```yaml
- ./config.py:/home/myapp/myapp/config.py
```

**结论：ConfigMap（生产）与 bind mount（开发）是同一种设计的两种投递方式。**

### 3.2 四个副本对照（实测）

| 文件 | 行数 | 用途 | K8s 生产是否生效 |
|---|---|---|---|
| `install/kubernetes/cube/overlays/config/config.py` | **921** | kustomize `configMapGenerator` 的源 | ✅ **就是它** |
| `install/docker/config.py` | 935 | docker-compose 的源 | ❌ |
| `py312/backup/config.py.install-docker.bak` | 927 | 迁移备份 | ❌ |
| `py312/backup/config.py.k8s-overlay.bak` | 913 | 迁移备份 | ❌ |

四份 md5 各不相同。**同名的 `entrypoint.sh`、`project.py` 也是多副本**
（`overlays/config/project.py` 与 `install/docker/project.py` 内容一致，但都 ≠ `myapp/project.py`）。

### 3.3 ConfigMap 是怎么"被设计出来"的

`install/kubernetes/cube/overlays/kustomization.yml`：

```yaml
configMapGenerator:
- name: kubeflow-dashboard-config
  files:
  - config/config.py
  - config/entrypoint.sh
  - config/project.py
# kubectl delete configmap kubeflow-dashboard-config -n infra
# kubectl create configmap kubeflow-dashboard-config --from-file=config -n infra
```

- 仓库里**没有任何 `kind: ConfigMap` 的 yaml**，它是 `kustomize build` 现生成的
- `configMapGenerator` 默认给名字加内容哈希后缀（如 `kubeflow-dashboard-config-kkg59f648t`），
  并同步改写 deployment 里的引用 → 配置一变自动滚动更新
- ⚠️ 上面注释掉的手动命令生成的名字**不带哈希**，和 deployment 引用对不上，改了等于没改

> **根因提示**：`config.py` 是**代码**（含 `import`、类定义），不是 key=value 配置。
> 把它放进 ConfigMap，就注定"镜像内版本"与"ConfigMap 版本"要手动同步。
> 历史上那次 `import imp` CrashLoop 就是这么来的（py3.12 移除了 `imp`，
> 镜像里改了、ConfigMap 里没改，启动即挂）。
> 旁边那个 `deploy-config` 才是正确示范——纯 `literals`，永远不冲突。

### 3.4 配置里的两个"注册表"

| 常量 | 位置 | 内容 |
|---|---|---|
| `CRD_INFO` | `config.py:601` | **10** 个自定义资源：`workflow` / `mpijob` / `tfjob` / `xgbjob` / `pytorchjob` / `virtualservice` / `vcjob` / `sparkjob` / `paddlejob` / `mxjob`，各带 `group/version/plural/kind/timeout` |
| `beat_schedule` | `config.py:530`（`CeleryConfig` 内） | 11 条定时任务（3 条被注释 → 8 条生效），见 §7.1 |

**`timeout` 是过期清理阈值**（如 workflow 是 `60*60*24*2` 秒），供 `delete_workflow` 使用。

## 4. Web 层骨架

### 4.1 views 层的"三件套"模式（贯穿全部 38 个 view 文件）

以 `view_notebook.py` 为例，每个业务模块都是同一个骨架：

```python
class Notebook_Filter(MyappFilter):          # ① 查询过滤器
    def apply(self, query, func): ...        #    :47

class Notebook_ModelView_Base():             # ② 纯 mixin，不继承 FAB，装全部业务逻辑
    def set_column(self, notebook=None)      #    :85  动态生成表单列
    def pre_add(self, item)                  #    :194 新增前加工
    def pre_update(self, item)               #    :249 修改前加工
    def post_add(self, item)                 #    :270 新增后落 K8s
    def pre_delete(self, item)               #    :844 删除前清 K8s
    @expose_api(url='/entry/jupyter')        #    :309 自定义路由
    def entry_jupyter(self): ...

class Notebook_ModelView_Api(                # ③ 组合成真正注册的 View
        Notebook_ModelView_Base,
        MyappModelRestApi):
    ...
```

**为什么要拆出 `_Base`？** 因为一个 Base 可以配多个 Api：
`Notebook` 有 `Notebook_ModelView_Api` 和 `Notebook_ModelView_SDK_Api`（`:889`、`:898`）；
`Pipeline` 有 `Pipeline_ModelView_Api` 和 `Pipeline_ModelView_Home_Api`（`:1309`、`:1334`）。
同一套业务逻辑，挂到不同 URL 前缀 / 不同权限。

**生命周期钩子全清单**（在 `baseApi.py:259-309` 定义为空实现，子类按需覆盖）：

```

pre_add / post_add / pre_add_req / pre_add_res / pre_add_web
pre_update / post_update / pre_update_req / pre_update_res / pre_update_web
```

### 9.2 ★ 后端驱动菜单（重要）

### 9.5 请求层的三个坑

`src/api/index.tsx`（174 行）：

1. **axios 实例没有设 `baseURL`** —— 第 5 行的 `const baseApi = process.env.REACT_APP_BASE_URL || 'http://localhost/'`
   是**死代码，从未被使用**。开发期靠 `src/setupProxy.js` 代理到 `http://localhost`
   （代理 `**/api/**`、`/myapp`、`/login`、`/users`、`/roles`、`/static/appbuilder`、`/pipeline_modelview`、`/project_modelview`）。
2. **鉴权靠 `myapp_username` cookie**，不是 `Authorization` header（缺 cookie 且不在 `/login` → 跳登录并 reject）。
3. **成功判定**是 `data.error_code === 0 || data.ret === 0`；响应头 `api_flashes`（数组 `[type, content]`）
   由响应拦截器取出弹通知 —— 这个头正是后端 `MyappModelRestApi.response()`（`baseApi.py:379`，header 设在 `:403`）塞的。

状态管理：**依赖了 mobx（`mobx@6` + `mobx-react-lite`），但没有实际全局 store**，页面状态一律 `useState`。**无 redux。**

## 11. 设计观察与风险点

| # | 观察 | 影响 |
|---|---|---|
| 1 | **`config.py` 是代码不是配置**，且存在 4 个互相不一致的副本 | 镜像与 ConfigMap 版本漂移 → 历史 CrashLoop 根因。改配置**必须两份一起改** |
| 2 | ConfigMap 名字带内容哈希后缀 | 手动 `kubectl create configmap` 生成的名字对不上，改了不生效。必须走 `kustomize build \| kubectl apply -f -` |
| 3 | `MyappModelRestApi` 的 30 层 `merge_response_func` 装饰器 | 加字段要同步改多个 `merge_*`，容易漏；但换来前端 `ADUGTemplate.tsx` 一套页面服务所有模块 |
| 4 | `home.py:menu()` 约 650 行的巨型函数 | 新增模块要动它；是导航中枢，改错全站菜单塌 |
| 5 | Model 层含大量 `*_html` 展示方法，且**没有统一基类、没有 `to_dict`、没有软删除** | 数据层不纯，元数据组装逻辑间接依赖，重构需谨慎 |
| 6 | `K8s` 类约 70 个方法集中于一个 2629 行文件 | 是**唯一**集群交互出口（好处）；但单文件过大，拆分时须保留 `make_pod` 的单一注入点语义 |
| 7 | `deploy-watch.yaml:140` 凌晨 3 点主动自杀式探针 | **有意为之**的每日回收（watch 偶发挂死），排障时别误判为 OOM |
| 8 | `get_volume_mounts` 是 `@staticmethod`，却依赖调用方传入 `username` 做卷展开 | 传错 username 会挂到别人的卷上，是**越权风险点** |
| 9 | `myapp/project.py` 同时承载 `push_message` 与 `MyCustomRemoteUserView` / `Myauthdbview` 登录视图 | 职责混杂；且它也是被 ConfigMap 覆盖的第三个文件 |
| 10 | **`adjust_node_resource` 在 per-cluster 循环里 `return`**（`schedules.py:1122/1130/1142/1152`） | 只在**第一个**集群生效。虽然该任务当前未被调度（见 §7.1），但重启它前必须先修 |
| 11 | `config_local.py:19-27` 把 `CELERY_CONFIG` 换成**没有 `beat_schedule`** 的 dict | **本地 docker-compose 一个定时任务都不触发**。排查"定时任务不生效"先看这里 |
| 12 | `CeleryConfig.target_annotations` 里的 `task.exec_command`（`config.py:518-524`）**全仓无实现** | 死配置项 |
| 13 | **`Pipeline` 继承 `ImportMixin` 却没有 `export_children=["task"]`** | 导出 pipeline **不会**递归带上 task。`ETL_Pipeline` 的两行也被注释掉了 |
| 14 | 表名与类名不一致：`RunHistory`→`run`、`Training_Model`→`model`、`Sqllab_Query`→`sqlab_query`（拼写就少一个 `l`） | 写原生 SQL / 查 migration 时容易踩 |
| 15 | `models/__init__.py` 为空，不做 re-export | "某张表在哪个文件"只能靠文件名猜，IDE 跳转差 |
| 16 | 前端 axios 实例**没有 `baseURL`**，`api/index.tsx:5` 那行 `baseApi` 是死代码；鉴权靠 `myapp_username` cookie | 换环境/加前缀时，代理人容易改错地方 |
| 17 | 前端依赖 mobx 但**没有实际全局 store** | 看 `store/` 目录会误以为有状态中心 |
