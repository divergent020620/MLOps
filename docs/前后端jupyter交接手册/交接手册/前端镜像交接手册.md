## 一、概述与适用范围

### 1.1 镜像定位

前端镜像职责 = **静态资源服务 + 反向代理后端**:

- 静态资源:`/frontend/`(cube-studio React 单页应用)、`/static/appbuilder/`(通用静态资源)
- 反向代理:其余路径转发到后端 Service `http://kubeflow-dashboard.infra/`(含 WebSocket 穿透)
- 根路径 `/` 301 重定向到 `/frontend/`

### 1.2 技术口径

| 项 | 口径 |
|---|---|
| Web 服务器 | nginx **1.21.5-5.p04**(麒麟源补丁版,**已被评估平台认可、零漏洞**) |
| 基座 | M0 基础基座镜像(行内 py12 麒麟基座 + 字体包,见 M0 章节),不基于旧前端镜像 |
| 产物形态 | 静态 dist(行外构建)+ nginx 配置(项目源码 `install/docker/dockerFrontend/` 原版) |
| 组装方式 | 容器 + docker commit(非 Dockerfile build,便于控制每一步并随时验证) |
| 漏洞红线 | **perl(超危 9.8)/ libtiff / libXpm / gd 一律不许进镜像;openssl-libs 零降级** |

### 1.3 适用场景

- 在行内麒麟信创环境,基于已送评的 M0 基座,重建/升级前端镜像
- 排查前端镜像 nginx 依赖、冒烟、上线问题
- 需要切换到 Caddy 备选方案时(见第七章)

## 二、nginx 版本决策过程(为什么最终走定向 rpm)

### 2.1 源内版本盘点

行内麒麟 yum 源中 nginx **只有 1.21.5-5 系列**(p01~p04 补丁版),没有更新版本。因此版本选择余地只有补丁号,最终取 **p04**(已送评认可)。

### 2.2 依赖解剖方法(判死 yum 路线的证明链)

用 rpm 元数据查询,而不是猜:

```bash
# 主包依赖了什么
rpm -qp --requires nginx-1.21.5-5.p04.ky10.x86_64.rpm
# 主包推荐(弱依赖)了什么
rpm -qp --recommends nginx-1.21.5-5.p04.ky10.x86_64.rpm
# 同法解剖 nginx-all-modules 及 5 个模块包
rpm -qp --requires nginx-all-modules-....rpm
rpm -qp --requires nginx-mod-http-perl-....rpm
```

解剖结论(2026-09 实测):

1. **nginx 主包硬依赖 `nginx-all-modules = 同版本`**(Requires,不是 Recommends);
2. `nginx-all-modules` **硬依赖全部 5 个动态模块包**:nginx-mod-http-perl、nginx-mod-http-image-filter、nginx-mod-http-xslt-filter、nginx-mod-mail、nginx-mod-stream;
3. 其中 perl / image-filter / xslt-filter 模块又拖入 **perl 5.28.3(超危 CVE 9.8)** 与 libtiff / libXpm / libX11 / libxslt / gd 等高危图形文本库;
4. 主包的 Recommends 区(C 区)为空——即不存在"只装主包"的弱依赖路径。

### 2.3 yum 最小化路线为何判死

原《前端镜像组装执行命令.md》方案是 `yum install nginx --exclude=nginx-all-modules,...`。实测(M2-1):**主包对 all-modules 是硬 Requires,exclude 之后依赖解析直接失败**——这正是原文档 FAQ 预判的失败模式。既然硬依赖无法用 exclude 绕过,而 all-modules 又必然拖入 perl 超危链,**yum 路线整体判死**,只能改走绕过依赖解析的定向 rpm 安装(方案 C1)或行外二进制(Caddy / 自编译)。

## 三、定向 rpm 安装方案(核心方案,方案 C1)

思路:**绕过 yum 依赖解析器,用 `rpm -ivh --nodeps` 手工装"主程序真正需要的最小集合"**。nginx 二进制实际运行只需要 nginx 主包 + nginx-filesystem(目录属主),再加 gperftools-libs + libunwind(满足 `libprofiler.so.0` 链接)。

### 3.1 起容器 + 基线

```bash
# <BASE_IMG> 换成本环境 M0 基座镜像
docker run -d --name fe-build01 <BASE_IMG> bash -c "sleep infinity"

docker exec -it fe-build01 bash
# 容器内:
rpm -qa | sort > /root/rpm_before.txt    # 基线,送评对照用
```

预期:`rpm_before.txt` 生成(本次基线 164 包,系统层与 M0 完全一致)。

### 3.2 先下载、后安装(downloadonly 到 /tmp/nrpm)

先用 yum 只下载不安装,便于逐个解剖与留档:

```bash
yum install -y --downloadonly --downloaddir=/tmp/nrpm \
  nginx nginx-filesystem gperftools-libs libunwind
ls -l /tmp/nrpm
```

预期:4 个 rpm 落盘:nginx-1.21.5-5.p04 / nginx-filesystem / gperftools-libs / libunwind。
(若 yum 因硬依赖解析失败拒下 nginx 主包,可改用 `yumdownloader --resolve` 或从行内源仓库目录直接取 rpm,关键是拿到上述 4 个文件。)

### 3.3 定向安装(--nodeps)

```bash
rpm -ivh --nodeps /tmp/nrpm/nginx-*.rpm /tmp/nrpm/nginx-filesystem-*.rpm
rpm -ivh /tmp/nrpm/gperftools-libs-*.rpm /tmp/nrpm/libunwind-*.rpm
```

说明:

- **nginx 主包 + nginx-filesystem 用 `--nodeps`**:唯一被剥离的就是对 all-modules 的元数据捆绑(其唯一作用是强拉 5 个动态模块,主程序不加载任何动态模块);
- gperftools-libs + libunwind 是真实运行依赖(nginx 链接 `libprofiler.so.0`),**正常安装、不走 nodeps**。

### 3.4 毒药零检查(送评前必须过)

```bash
nginx -v
# 预期:nginx version: nginx/1.21.5

rpm -qa | grep -E "^(perl|perl-libs|libtiff|libXpm|gd|nginx|gperftools|libunwind)" | sort
# 预期:仅 4 个新增包(nginx/nginx-filesystem/gperftools-libs/libunwind),
#       perl*/libtiff/libXpm/gd 一行都不许出现

# 确认 openssl-libs 没有被动过(必须保持基座 p34)
rpm -q openssl-libs
# 预期:1:1.1.1f-31.p34...(与基线一致,零降级——优于原方案预期的 p29 降级)

# rpm diff 总核对(⚠ 基座精简容器内没有 diff 命令,实测踩坑,用 python3 对比)
rpm -qa | sort > /root/rpm_after.txt
python3 -c 'a=set(open("/root/rpm_before.txt").read().split()); b=set(open("/root/rpm_after.txt").read().split()); print("新增:",sorted(b-a)); print("移除:",sorted(a-b))'
# 预期:仅 4 个新增包,0 移除,零 Downgrading
```

任何 perl/libtiff/libXpm/gd 出现 → **停止,回滚重来,不得送评**。

## 四、配置与静态产物合流

### 4.1 配置写入

材料取自项目源码 `install/docker/dockerFrontend/`(项目原版,不手写):

| 源文件 | 容器内目标 | 作用 |
|---|---|---|
| `nginx.conf` | `/etc/nginx/nginx.conf` | 主配置:worker 8、epoll、51200 连接、5GB body、gzip、`user nginx;` |
| `nginx.80.conf` | `/etc/nginx/conf.d/default.conf` | server 块:80 端口、`/`→`/frontend/` 重定向、两个静态 location、反代 `kubeflow-dashboard.infra` |

```bash
docker cp nginx.conf        fe-build01:/etc/nginx/nginx.conf
docker cp nginx.80.conf     fe-build01:/etc/nginx/conf.d/default.conf
```

注意:`nginx.conf` 首行是 `user nginx;`——**镜像内必须存在 nginx 用户**,否则启动报 `getpwnam("nginx") failed`:

```bash
# 容器内(rpm 装包时若因 --nodeps 未建用户则手工补)
useradd -r -s /sbin/nologin nginx 2>/dev/null || true
id nginx
# 预期:uid=...(nginx)
```

### 4.2 静态产物合流

dist 来源(本次):`cube312-prod-pack/myapp/static/appbuilder/frontend`(6.4M,React 构建产物)与 `myapp/static`(30.6M):

```bash
mkdir -p /data/web /data/log/nginx
docker cp <frontend-dist目录>/. fe-build01:/data/web/frontend/
docker cp <static目录>/.        fe-build01:/data/web/static/

# 按旧链口径删除两个多余文件(与 Dockerfile.kylin 一致)
docker exec fe-build01 rm -f /data/web/frontend/manifest.json /data/web/frontend/robots.txt

docker exec fe-build01 ls /data/web/frontend | head
# 预期:index.html 及静态资源在位
```

### 4.3 配置自检

```bash
docker exec fe-build01 nginx -t
# 预期:syntax is ok / test is successful
# ⚠ 若报 kubeflow-dashboard.infra 解析失败,见第五章(容器内无集群 DNS,属预期,不要改配置)
```

## 五、冒烟测试

### 5.1 容器内启动失败:DNS 解析不了 kubeflow-dashboard.infra

`nginx.80.conf` 中 `proxy_pass http://kubeflow-dashboard.infra/;` 的主机名是 **K8s 集群内 Service 名,只有集群 DNS 能解析**。构建机上的普通 docker 容器没有集群 DNS,`nginx -t` / 启动会报 `host not found in upstream`。**这是环境差异,不是配置错误**——部署到 K8s 后天然成立,**不要为此改 nginx 配置**。

临时验证法:容器内 `/etc/hosts` 加一条映射(指向任意可达地址,能过解析即可):

```bash
docker exec fe-build01 bash -c 'echo "<某可达IP>  kubeflow-dashboard.infra" >> /etc/hosts'
docker exec fe-build01 nginx -t      # 预期:ok
```

### 5.2 启动与静态页验证

```bash
docker exec -d fe-build01 nginx -g "daemon off;"
docker exec fe-build01 curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/frontend/
# 预期:200,内容为 cube-studio React index.html

docker exec fe-build01 curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/frontend/
docker exec fe-build01 curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/static/
# 预期:目录本身 403 —— autoindex off 禁目录遍历,与旧链一致,属预期
#       (具体静态文件应逐个 curl 到 200)
```

**目录 403 是正常行为**:`autoindex off` 是刻意的安全配置,只要具体文件路径 200 即通过。

### 5.3 hosts 清理:bind mount 坑与截断重写法

**坑:`/etc/hosts` 在容器内是 docker 的 bind mount 文件,`sed -i` 原地编辑会报 `Device or resource busy`(EBUSY),且 sed -i 的临时文件替换机制可能失效。**

正确做法——截断重写法:

```bash
docker exec fe-build01 bash -c 'grep -v "kubeflow-dashboard.infra" /etc/hosts > /tmp/hosts.new && cat /tmp/hosts.new > /etc/hosts && rm /tmp/hosts.new'
docker exec fe-build01 cat /etc/hosts   # 预期:无残留映射
```

要点:用 `cat >` **覆写内容**(inode 不变,bind mount 不受影响),而不是替换文件。commit 前必须确认 hosts 无残留,否则映射会被固化进镜像。

## 六、commit 与 K8s 上线

### 6.1 commit(全新 tag,不覆盖任何原镜像)

```bash
docker stop fe-build01
docker commit \
  --change 'CMD ["nginx", "-g", "daemon off;"]' \
  fe-build01 <registry>/kubeflow-dashboard-frontend:fe-nginx-test-v1
# 本次实例:10.240.125.39/kubeflow-dashboard-frontend:fe-nginx-test-v1
```

要点:

- **CMD 必须是 `nginx -g "daemon off;"`(前台运行)**,否则容器起完即退。项目里 start.sh 的其他行(mkdir 日志目录等)如需要可一并纳入,本次直接用 CMD 简化;
- tag 一律全新,不动任何已有 tag(安全纪律)。

### 6.2 新镜像验证 + 导出送评

```bash
docker run -d --name fe-verify <registry>/...:fe-nginx-test-v1
docker exec fe-verify nginx -v                        # 1.21.5
docker exec fe-verify curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/frontend/   # 200
docker exec fe-verify cat /etc/hosts                  # 无残留
docker exec fe-verify ls /data/web/frontend /data/web/static   # 在位
docker rm -f fe-verify

docker save -o /bdm/images-kylin/fe-nginx-test-v1.tar <registry>/...:fe-nginx-test-v1
# 附 rpm 清单(送评材料):容器内 rpm -qa | sort > fe-rpm-after.txt
```

### 6.3 push + K8s 切换(set image)

```bash
docker push <registry>/kubeflow-dashboard-frontend:fe-nginx-test-v1

kubectl set image deployment/kubeflow-dashboard-frontend \
  kubeflow-dashboard-frontend=<registry>/kubeflow-dashboard-frontend:fe-nginx-test-v1 -n infra \
  && kubectl rollout status deployment/kubeflow-dashboard-frontend -n infra --timeout=180s
# 预期:successfully rolled out

# 验证
kubectl get pods -n infra | grep frontend
# 预期:双副本 1/1 Running
kubectl exec -n infra deploy/kubeflow-dashboard-frontend -- \
  curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/frontend/
# 预期:200(JS 资源抽验同法,亦应 200)
```

### 6.4 回滚

```bash
kubectl rollout undo deployment/kubeflow-dashboard-frontend -n infra
# 或显式 set image 回旧 tag(kylin-20260730)
kubectl rollout status deployment/kubeflow-dashboard-frontend -n infra
```

前端镜像不含状态、不含 ConfigMap 依赖,回滚 = 一条 set image,分钟级完成。

## 七、Caddy 备选方案

### 7.1 何时启用

- 定向 rpm 方案不可用时(如行内源下架 1.21.5-5 系列、或平台不再认可该版本);
- 或希望**零 rpm 新增、零降级**的更干净系统层(Caddy 为 Go 静态二进制,无任何动态依赖)。

### 7.2 材料准备

- 行外下载 Caddy 官方预编译 linux_amd64(本次备选版为 v2.9.1),与 Caddyfile 一起打包为 `fe-caddy-kylin.tgz`;
- ⚠ 本次交接包中 **`materials/` 目录缺失,`fe-caddy-kylin.tgz` 未随包交付**——启用前需向交接人索取或按 Caddy 方案文档重新制作(Windows 下载 → 网闸传入行内)。

### 7.3 行内装配要点

```bash
docker run -d --name fe-caddy01 <BASE_IMG> bash -c "sleep infinity"
docker cp fe-caddy-kylin.tgz fe-caddy01:/tmp/
docker exec -i fe-caddy01 bash -c '
set -e
mkdir -p /tmp/fe && tar xzf /tmp/fe-caddy-kylin.tgz -C /tmp/fe
cp /tmp/fe/caddy /usr/local/bin/caddy && chmod +x /usr/local/bin/caddy
mkdir -p /etc/caddy /data/web /data/log/caddy
cp /tmp/fe/Caddyfile /etc/caddy/Caddyfile'
# 静态产物 docker cp 到 /data/web/(同第四章)
# 验证:
/usr/local/bin/caddy version          # v2.9.1
/usr/local/bin/caddy fmt /etc/caddy/Caddyfile --diff && echo "语法 OK"
# commit 时 CMD 改为: /usr/local/bin/caddy run --config /etc/caddy/Caddyfile
```

### 7.4 与 nginx 配置语义对照

| nginx(nginx.80.conf) | Caddy(Caddyfile) |
|---|---|
| `location = /` rewrite → `/frontend/` permanent | `redir / /frontend/ permanent` |
| `location /frontend/` + `root /data/web` + `try_files ... /frontend/index.html` | `handle /frontend/*` { root * /data/web; file_server; try_files {path} {path}/ /frontend/index.html } |
| `location /static/appbuilder/` 同上 | `handle /static/appbuilder/*`(可并入同一 handle) |
| html `add_header Cache-Control no-cache` | `header @html Cache-Control "no-cache, no-store"`(path_regexp 匹配 .html) |
| `proxy_pass http://kubeflow-dashboard.infra/` + Upgrade/Connection 头 | `reverse_proxy http://kubeflow-dashboard.infra`(**WebSocket 自动透传,无需手配**) |
| `proxy_read/send_timeout 3600s` | transport `read_timeout/write_timeout 3600s` |

注意:nginx 的 `user nginx;` / nginx 用户创建等问题在 Caddy 方案下不存在(root 直接运行,绑 80 无 CAP 问题);TLS 方面 Caddy 自动证书需外网 ACME,行内环境用 http + 网关补 TLS。

## 九、潜在问题与坑(全面清单)

1. **perl / libtiff / libXpm / gd 毒药清单**:nginx 全模块安装(yum 默认)会拖入 perl 5.28.3(超危 9.8)+ libtiff/libXpm/libX11/libxslt/gd 高危链。任何环节发现这些包出现在 `rpm -qa` 即失败,禁止送评。
2. **主包硬依赖 all-modules**:`nginx` 主包 Requires `nginx-all-modules = 同版本`(非 Recommends),`--exclude` 最小化装法必然解析失败——不要在 yum exclude 上浪费时间,直接走 rpm --nodeps。
3. **--nodeps 的 rpmdb 未满足记录**:nodeps 安装后 rpmdb 会留有未满足的 requires(nginx 对 openssl CLI、对 all-modules)。这是**元数据层面**的记录,功能无影响,送评时附第十章豁免说明。共 5 条,见第十章。
4. **libprofiler 依赖必须真实补**:nginx 二进制链接 `libprofiler.so.0`(gperftools-libs,其又需 libunwind)。这两个包**正常安装、不要 nodeps**,否则启动报库缺失。
5. **openssl-libs 保持基座零降级**:本次定向方案实测 openssl-libs 维持基座 **p34**,零降级(优于原 yum 方案文档预期的降到 p29——那是 yum 装法强拉 openssl 包导致的)。核对时 `rpm -q openssl-libs` 必须与基线一致。
6. **`user nginx;` 需建用户**:nginx.conf 首行声明 nginx 用户;--nodeps 安装可能未自动建户,缺用户时启动报 `getpwnam("nginx") failed`,手工 `useradd -r -s /sbin/nologin nginx`。
7. **proxy_pass 主机名在启动时解析**:`proxy_pass http://kubeflow-dashboard.infra/` 中的域名在 **nginx 启动/ reload 时**就要求可解析(不是请求时)。构建机容器无集群 DNS → `nginx -t` 报 `host not found in upstream`。处理:临时 /etc/hosts 映射验证,**不改配置**;K8s 内集群 DNS 天然可解析。
8. **autoindex off 目录 403 是正常**:curl 目录本身返回 403 是 `autoindex off`(禁目录遍历)的预期行为,与旧链一致;验证应针对具体文件路径期望 200。
9. **/etc/hosts 是 bind mount,`sed -i` 会 EBUSY**:`sed -i` 通过临时文件+rename 替换,对 bind mount 文件报 `Device or resource busy`。清理残留必须用**截断重写法**(`grep -v ... > tmp && cat tmp > /etc/hosts`)。commit 前必须确认无残留,否则映射固化进镜像。
10. **manifest.json / robots.txt 删除口径**:与旧链 Dockerfile.kylin 一致,`/data/web/frontend/` 下的这两个文件要删(避免暴露构建元信息)。
11. **dist 材料依赖**:前端 dist 属行外构建产物,不会随交接包自动到位;材料未到前 nginx/配置部分可先行,dist 合流必须等交付并核对来源目录。
12. **commit 用全新 tag**:一律新 tag(如 fe-nginx-test-v1),不覆盖任何原镜像 / 原 tar;`docker tag` 仅是别名,不算修改。
13. **工作容器收尾**:commit 并验证后 `docker rm fe-build01`;挂起期间保留不删。
14. **送评对照口径**:M2 系统层与 M0 完全一致(仅多 4 个 nginx 相关包),M0 送评结论可直接覆盖 M2 系统层;rpm 清单文件(fe-rpm-after.txt)随 tar 一并交付。

## 十、送评豁免说明(定向 rpm 安装,共 5 条)

以下 5 条为 M2 前端镜像送评时必附的豁免说明(引自《操作流程记录.md》第九节"送评要点",2026-09 定稿口径):

> **M2 前端豁免说明(必附)**:
> ① nginx 1.21.5-5.p04 为平台已认可版本;
> ② yum 解析器强制捆绑 all-modules→perl 5.28.3(超危 9.8),故 `rpm -ivh --nodeps` 定向安装,剥离 all-modules 及全部动态模块(主程序不加载任何模块,静态+反代场景功能完整,`nginx -t` 与实际启动均验证);
> ③ 镜像仅 4 个新增 rpm:nginx / nginx-filesystem / gperftools-libs / libunwind;
> ④ openssl-libs 保持基座 p34 **零降级**(优于前端方案文档预期的 p29);
> ⑤ 基座无 openssl CLI,主包一条 requires 元数据未满足,运行无影响。

补充背景(操作记录 M2-4 原文):--nodeps 剥离的 all-modules 元数据捆绑,唯一作用是强拉含超危 perl 的 5 个模块,主程序不加载任何动态模块;gdbm 报告属 GNU dbm 误报,非图形库 gd。
