## 一、概述与适用范围

- **镜像定位**:M1 后端镜像 = M0 基础基座 + py3.12 venv(锁定版 Python 依赖)+ myapp 源码 + keytab/krb5.conf。**同一个镜像供 4 个 deployment 共用**(与旧链一致):
  - `kubeflow-dashboard`(生产流量入口,gunicorn)
  - `kubeflow-dashboard-schedule`(celery beat/探针)
  - `kubeflow-dashboard-worker`(celery worker,2 副本)
  - `kubeflow-watch`(supervisord:watch-service/watch-workflow)
- **分层结构**:
  ```
  行内 py12 基座 ──► M0 基础基座(app-base-test-v1:kinit + libkadm5srv + 字体)
                        ├──► M1 后端镜像(本文:venv + myapp)   ◄── 4 deployment 共用
                        ├──► M2 前端镜像(nginx + dist)
                        └──► M3 jupyter 镜像(venv + jupyterlab)
  ```
- **基座依赖**:必须先完成 M0(kinit 二进制、libkadm5srv 库、fontconfig/wqy-microhei 字体、零降级纪律),后端镜像 FROM M0。M0 送评一次达标 ⇒ 后端镜像系统层同步达标(后端自身零新增 rpm,仅 M0 的 7 个字体包为"新增")。
- **验收标准**:`/opt/appenv/bin/python -c "import myapp"` OK + HDFS-Kerberos 断言 OK;最终以 K8s 切换后 Pod 稳定 + `/health` 200 为准。

## 三、M0 基础基座构建(简述)

M0 是后端镜像的 FROM,要点如下(详见《行内组装执行命令.md》)。

1. **起容器驻留**:`docker run -d --name app-base-build01 <行内基座:tag> bash -c "sleep 3600"`(不要 `--rm`,要 commit)。
2. **krb5 保全(方案 A,推荐)**:不装 krb5-workstation 包,而是 `yum install -y --downloadonly krb5-workstation` → **立刻**把 `/var/cache/dnf` 下 rpm 转移(dnf 缓存"下个成功事务即清")→ `rpm2cpio *.rpm | cpio -idm` 解包,只提取 `/usr/bin/kinit` 和 `libkadm5srv_mit.so.12*` 拷入 + ldconfig。效果:krb5-libs 保持原版**零降级**,rpmdb 无变化。cpio 用完 `rpm -e cpio` 卸掉。
3. **装字体(前后端/jupyter 共用)**:带 EXCL 防降级名单安装:
   ```bash
   EXCL="glibc,glibc-common,libxml2,openssl-libs,curl,libcurl,pam,libssh,libarchive,cyrus-sasl-lib,libstdc++,libgcc,expat,zlib,libtasn1,ncurses-libs,libuuid,util-linux,systemd-libs,libseccomp,sqlite-libs,bzip2-libs,xz-libs,libzstd,gnutls,nettle,libgcrypt,libidn2,libnghttp2,libpsl"
   yum install -y fontconfig wqy-microhei-fonts --exclude=$EXCL
   # 预期:Transaction Summary 只有 Installing:,无任何 Downgrading
   ```
4. **EXCL 防降级纪律**:行内源比基座旧(glibc p12/openssl-libs p34/krb5-libs 23 都比源新),所有 yum 命令必须带 EXCL;出现 Downgrading 行即停,记录交回。
5. **rpm diff 验证**:`rpm -qa | sort` 前后对比,只应新增 fontconfig/wqy-microhei 及其依赖 7 包。
6. **commit + save**:全新 tag `app-base-test-v1` → `docker save` 导 tar → 送评(立即送,不等其他镜像)。

## 四、后端镜像构建

### 4.1 两种方式对比

| | 方式 B:Dockerfile 法 | 方式 A:容器 + commit 法(本次实际采用) |
|---|---|---|
| 过程 | `docker build -f Dockerfile.backend-py312 .` | 起容器手动执行同等步骤后 commit |
| 优点 | 步骤固化,断言内建 | **容器内 pip 缓存可累积**,Nexus 404 重跑即推进;增量修复(整改只需改一处重 commit) |
| 缺点 | 每次失败整体重来、无 pip 缓存,与 Nexus 回源抖动特性相性极差;本次 3 次失败后放弃 | 手工步骤多,需逐项核对(docker cp 多源坑) |

**Dockerfile 法的已知缺陷 4 处及修法**(均为交付包原件问题,已反馈):

1. `requirements-kerberos.txt` 文件内嵌 `--no-deps` 选项行 → pip 25 报 `Invalid requirement: --no-deps`。**修法**:删除该行(命令行本已带 `--no-deps`,语义不变)。
2. Dockerfile ③ 主依赖步钉 `wtforms-json==0.3.5`,行内源仅有 0.3.4(0.3.5 是同事重打 wheel,在 offline-wheels/),③ 步只查源不查 wheel。**修法**:③ 步加 `--find-links /tmp/ow`(不动版本钉子)。
3. 构建期断言在 build 内必然失败:包内 myapp/config.py **故意置空**(0 字节),且 import myapp 需要 MYSQL_SERVICE。**修法**:冒烟需临时配置(见 4.2 冒烟方法)。
4. Dockerfile 无 `WORKDIR /home/myapp`、无 `RUN mkdir -p /var/log/supervisor`(与方式 B 无关的镜像缺陷,方式 B 构建出来上线同样崩)。**修法**:分别用 deployment workingDir patch 与 v6 镜像内 mkdir 规避,长期应进 Dockerfile。

另有执行顺序坑:依赖安装必须 **③主依赖 → ④离线4包**(wtforms-json 依赖 ③ 装的 WTForms,Dockerfile "顺序不可乱"注释属实)。① gssapi/decorator ② kerberos 组 → ③ 主依赖 → ④ wtforms_json/jieba/hdfs/docopt。

### 4.2 容器 + commit 法完整命令序列

**起容器**(注意:sleep 3600 到时容器退出,长操作需重启或加大时长):

```bash
docker run -d --name app-p312-01 <registry>/kubeflow-dashboard:app-base-test-v1 bash -c "sleep 3600"
docker ps | grep app-p312-01     # 预期:UP
```

**材料入容器(逐个 cp,docker cp 不支持多源!)**:

```bash
# ⚠ docker cp a.txt b.txt c:/tmp/ 会报错,一条命令只能一个源
docker cp requirements-final.txt      app-p312-01:/tmp/requirements-final.txt
docker cp requirements-kerberos.txt   app-p312-01:/tmp/requirements-kerberos.txt
docker cp offline-wheels              app-p312-01:/tmp/ow
docker cp myapp                       app-p312-01:/home/myapp/myapp
docker cp ai_general.keytab           app-p312-01:/home/myapp/ai_general.keytab
docker cp krb5.conf                   app-p312-01:/etc/krb5.conf
# 每条后可在容器内 ls 核对;漏拷 keytab/krb5.conf 会产出缺陷镜像(本次 v1 教训)
```

**venv + 四步依赖安装(顺序不可乱 ①②③④)**:

```bash
docker exec -i app-p312-01 bash -c '
set -e
python3.12 -m venv /opt/appenv
# ① SPNEGO 原生后端(离线)
/opt/appenv/bin/pip install --no-index --find-links /tmp/ow gssapi decorator
# ② Kerberos 组(行内源,必须 --no-deps;文件内若残留 --no-deps 行须先删)
/opt/appenv/bin/pip install --no-deps --trusted-host <nexus-host> --index-url "$PIP_IDX" \
    -r /tmp/requirements-kerberos.txt
# ③ 主依赖 63 包(行内源,全 wheel;find-links 补 wtforms-json 0.3.5)
/opt/appenv/bin/pip install --only-binary=:all: --find-links /tmp/ow \
    --trusted-host <nexus-host> --index-url "$PIP_IDX" -r /tmp/requirements-final.txt
# ④ 4 个 sdist-only 纯 py 包(离线)
/opt/appenv/bin/pip install --no-index --find-links /tmp/ow wtforms_json jieba hdfs docopt
echo ALL DEPS OK'
# 预期:ALL DEPS OK;Nexus 404 抖动时原样重跑即推进(容器内缓存有效)
```

**冒烟断言(两道)**——包内 myapp/config.py 故意置空,适配版在 k8s-config/;冒烟方法 = 把 k8s-config/config.py 拷为容器内 smokeconfig.py,环境变量指过去 + SQLite 临时连接串,**不碰 myapp 源码,冒烟后删除**:

```bash
docker cp k8s-config/config.py app-p312-01:/home/myapp/smokeconfig.py
docker exec -i app-p312-01 bash -c '
cd /home/myapp && PYTHONPATH=/home/myapp MYAPP_CONFIG=smokeconfig MYSQL_SERVICE="sqlite://" \
  /opt/appenv/bin/python -c "import myapp; print(\"myapp import OK\")"
PYTHONPATH=/home/myapp /opt/appenv/bin/python -c \
  "import gssapi; from hdfs.ext.kerberos import KerberosClient; KerberosClient(\"http://x:50070\", timeout=10); print(\"HDFS-Kerberos OK\")"
rm /home/myapp/smokeconfig.py'
# 预期:myapp import OK + HDFS-Kerberos OK
```

**clean(清缓存)+ rpm 核对**:

```bash
docker exec -i app-p312-01 bash -c '/opt/appenv/bin/pip cache purge; \
  rpm -qa | sort > /root/rpm_after.txt'
# ⚠ 基座精简容器内没有 diff 命令(实测踩坑)!对比用 python3:
docker exec -i app-p312-01 python3 -c 'a=set(open("/root/rpm_before.txt").read().split()); b=set(open("/root/rpm_after.txt").read().split()); print("新增:",sorted(b-a)); print("移除:",sorted(a-b))'
# 预期:与 M0 最终态一致(仅 M0 的 7 个字体包为新增),后端自身 rpm 零变化
```

**commit(--change 注入 ENV/CMD)**:

```bash
docker stop app-p312-01
# ⚠ ENV PATH 必须写完整字面值:$PATH 在单引号/commit 解析中不会展开,
#   本次实例完整值为(基座 PATH 前插 /opt/appenv/bin:/home/myapp/myapp/bin):
#   /opt/appenv/bin:/home/myapp/myapp/bin:/opt/python3.12.10-x86_64-bin/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
docker commit \
  --change 'ENV PATH=/opt/appenv/bin:/home/myapp/myapp/bin:/opt/python3.12.10-x86_64-bin/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin' \
  --change 'ENV PYTHONPATH=/home/myapp' \
  --change 'ENV MYAPP_HOME=/home/myapp' \
  --change 'CMD ["bash","/entrypoint.sh"]' \
  app-p312-01 <registry>/cube-studio/kubeflow-dashboard:app-p312-test-v2
# 预期:新 tag 生成;随后验证:docker run --rm <新镜像> bash -c 'echo $PATH' 
#       应以 /opt/appenv/bin 开头;容器内 keytab(400B)/krb5.conf(905B,非基座 587B 默认件)对账
docker save -o /bdm/images-kylin/app-p312-test-v2.tar <registry>/cube-studio/kubeflow-dashboard:app-p312-test-v2
docker rm app-p312-01
```

**压扁(export + import)**——原因:docker 删除文件是 whiteout,物理数据仍在底层(v3 删 frontend 后 tar 仍 2.4G,内含 node_modules 约 1G);压扁为单层后体积 2.4G→1.4G,敏感内容物理消失:

```bash
docker export app-flat-01 -o /tmp/flat.tar        # 从修复版容器导出(容器保持运行)
cat /tmp/flat.tar | docker import \
  --change 'ENV PATH=/opt/appenv/bin:/home/myapp/myapp/bin:/opt/python3.12.10-x86_64-bin/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin' \
  --change 'ENV PYTHONPATH=/home/myapp' \
  --change 'ENV MYAPP_HOME=/home/myapp' \
  --change 'CMD ["bash","/entrypoint.sh"]' \
  - <registry>/cube-studio/kubeflow-dashboard:app-p312-test-v4
# ⚠ 同上:ENV PATH 写完整字面值,$PATH 不展开;export/import 会丢原镜像配置,
#   所有 ENV/CMD 必须用 --change 重新注入
# 预期:镜像约 1.4G;复验:myapp import OK、frontend 目录不存在、PATH 正确
rm /tmp/flat.tar
```

## 六、K8s 上线切换

### 6.1 ConfigMap 前置原理(最硬的前提)

现网旧 ConfigMap 的 config.py 是旧版,内含 **`import imp`**——py3.12 已移除 imp 模块,**新镜像配旧 cm 启动即崩**。必须先上适配版三件套(config.py:imp→importlib、CACHE_TYPE=RedisCache、CLUSTERS 含 prod;entrypoint.sh:幂等补缺表;project.py)。**这是"唯一必须先做的硬动作"**。

材料路径注意:适配版在交付包 `k8s-config/`,**不是** `install/kubernetes/cube/overlays/config/`(后者实测为 8-24 旧版,仍含 import imp)。

### 6.2 原子 patch 法(镜像 + 卷引用一拍切换)

现网 4 个 deployment 挂的是**哈希名 cm**(如 `kubeflow-dashboard-config-kkg59f648t`),直接 `kubectl create` 裸名 cm 不会生效,直接 `set image` 则新镜像配旧 cm 必崩(本次曾拦截同事的 4 条 set image 命令)。正确做法:**建独立新 cm + strategic patch 同拍改"卷引用 + 镜像"**,不产生"新镜像配旧配置"中间态:

```bash
# 1) 回滚手册先落盘(先写后切),内容含 4 条 set image 回旧 tag + 卷名改回哈希名
# 2) push 镜像到 Harbor(kubelet 只认仓库)
docker push <registry>/cube-studio/kubeflow-dashboard:app-p312-test-v6
# 3) 侦察卷名/容器名(patch 输入)
for d in kubeflow-dashboard kubeflow-dashboard-schedule kubeflow-dashboard-worker kubeflow-watch; do
  echo "== $d =="; kubectl get deploy -n infra $d -o jsonpath='{range .spec.template.spec.volumes[*]}{.name}{" -> "}{.configMap.name}{"\n"}{end}{"容器: "}{.spec.template.spec.containers[*].name}{"\n"}'; done
# 4) 建新 cm(三件套来自交付包 k8s-config/)
kubectl create configmap kubeflow-dashboard-config-py312 -n infra \
  --from-file=config.py=<路径>/k8s-config/config.py \
  --from-file=entrypoint.sh=<路径>/k8s-config/entrypoint.sh \
  --from-file=project.py=<路径>/k8s-config/project.py
# 验证:第一行必须是 importlib,不得出现 import imp
kubectl get cm -n infra kubeflow-dashboard-config-py312 -o jsonpath='{.data.config\.py}' | head -3
```

## 八、潜在问题与坑(全面清单)

1. **EXCL 防降级名单**:行内源比基座旧(glibc p12 / openssl-libs p34 / krb5-libs 23 均比源新),所有 yum 命令必须带全量 EXCL 名单(见第七章);出现任何 `Downgrading:` 行立即停,记录交回,不自行处理。
2. **Nexus 404 抖动**:大 wheel 首拉回源超时易 404(本次 numpy/pyarrow/scikit-learn/cryptography 均遇到),**原样重跑即过**;docker build 无缓存放大该问题(每次失败整体重来)——这是改走容器+commit 流的主因;容器流可加 `--timeout 60 --retries 5`。
3. **docopt 无 wheel**:PyPI 仅源码包,`--only-binary=:all:` 会挡住 → ResolutionImpossible。处理:加 `--no-binary docopt`(纯 Python 包,无需 gcc,不改变版本选择)。
4. **pip 校验 wheel 文件名**:wheel 改名(如 cube_studio_dataset-2.0.0.whl 改 csd.whl)会报 invalid——文件名必须保持标准命名。
5. **docker cp 不支持多源**:`docker cp a.txt b.txt c:/tmp/` 报错,且**一条多源命令失败可能连带后续拷贝被跳过**——本次 v1 镜像缺 keytab、krb5.conf 未更新的根因。必须逐个 cp 并逐项核对。
6. **sleep 3600 容器超时退出**:长操作(依赖安装+送评整改)期间容器可能静默退出,commit 前务必 `docker ps` 确认 UP;退出则 `docker start` 恢复(容器层还在)。
7. **导 tar 后白化层问题**:docker rm 文件只是 whiteout,物理数据仍在镜像层(删 frontend 后 tar 仍 2.4G、node_modules 还在)——安全整改删除类必须 `docker export + import` 压扁单层。
8. **rollout 卡住时挑错 pod**:`kubectl rollout status` 卡住不代表失败,新 pod 可能 CrashLoopBackOff;用 `kubectl get pods` 找非 Running 的新 pod → `kubectl logs <pod> --tail=50` 看真实报错(本次 watch 的 supervisor 目录、dashboard 的 workingDir 均如此定位)。
9. **中文输入法尾字符混入 URL**:人工 curl 验证时命令尾误带中文标点(如 "、"),返回 404 页,易误判为服务故障——先检查命令本身。
10. **旧 cm 哈希名**:现网 deployment 挂哈希名 cm(如 `-kkg59f648t`),建裸名同名 cm 不生效;必须新 cm + patch 卷引用;旧 cm 切换后**保留**(回滚安全网),稳定数天后再删。
11. **entrypoint 写库动作风险**:entrypoint.sh 含 create_db / db upgrade / create-admin / 幂等补表等**写库步骤**(由 ConfigMap 注入,不在镜像);并行测试 Pod 必须 command 覆盖为只读检查(gunicorn+check_tables),直连生产库动作只允许在正式切换窗口执行;`Duplicate column` 日志属 try/except 设计内,忽略。
12. **镜像内 config.py 故意置空**:import myapp 需 MYAPP_CONFIG/MYSQL_SERVICE,Dockerfile 构建期断言必失败;冒烟用临时 smokeconfig + sqlite。
13. **基座精简缺件**:麒麟精简基座无 `/var/log/supervisor`(supervisord.conf 钉死该路径)、无 hostname 命令(entrypoint echo 装饰用,非致命)、无 openssl CLI(nginx requires 元数据未满足但无运行影响)。
14. **无 WORKDIR**:entrypoint 相对路径在 / 下解析失败 → dashboard CrashLoop;deployment workingDir patch 规避,长期进 Dockerfile。
15. **pip 25 不支持文件内选项行**:requirements 文件内嵌 `--no-deps` 报 Invalid requirement,删行(命令行带即可)。
16. **wtforms-json 0.3.5 只在 offline-wheels**:行内源仅 0.3.4,③ 步必须 `--find-links`;且顺序必须 ③→④(依赖 WTForms)。
17. **registry 路径别名**:Dockerfile FROM 与本机镜像路径不一致时 `docker tag` 加别名,无需重建。
18. **profile.d PATH 补救在 K8s 无效**:K8s 容器非登录 shell,`/etc/profile.d` 不生效;PATH 必须用镜像 ENV(commit/import --change)。
19. **cryptography 升级连带**:46.0.5 要求 cffi ≥2.x,升级后 pip check 复验;母包 requirements 钉子需同步更新,否则下次构建回退 45.0.4。
