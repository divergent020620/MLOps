## 3. 架构介绍

### 3.1 总体架构

```
用户浏览器
   │
   ▼
Istio IngressGateway（入口网关）
   │
   ├──► kubeflow-dashboard-frontend（nginx，托管 React 静态文件）
   │       ├── /frontend/*  → 前端 SPA 静态资源
   │       └── /*           → 反向代理到后端
   │
   └──► kubeflow-dashboard（Flask + gunicorn，后端）
           ├── MySQL 8.0（主库，SQLAlchemy ORM）
           ├── Redis（缓存 + Celery broker）
           │     ├── Celery beat   — 定时任务（清理、定时 pipeline、GPU 监控）
           │     ├── Celery worker — 异步任务（镜像构建、notebook 提交、资源查询）
           │     └── watch         — 监听 Argo Workflow 状态并回写 DB
           ├── K8s API Server — 所有工作负载最终都变成 K8s 资源

```

## 5. 当前最重的工作：信创国产化改造 ★

> 这是目前投入人力最多的方向，也是新同事最可能被分配到的战场。相关文档集中在 `fix/`（镜像安全）与 `py312/`（Python 迁移）两个目录。

### 5.1 行内口径（先记住这三条）

1. **评估工具**：奇安信开源卫士，扫描镜像里的所有组件（rpm / pip / npm 包）。
2. **管控策略**：**高危及以上组件禁止**。我们的整改范围就锁定在**超危 + 高危**，中危/低危不处理。
3. **整改是循环的**：改镜像 → 送评 → 拿报告 → 销项 → 再送评，直到超危/高危清零（豁免项除外）。

**硬约束**：

- 行内要求**必须使用 Python 3.12**，3.9 不再允许。
- 行内统一麒麟基座为 `kylinv10sp3-python312`，**不能带出行内**，只能在行内组装镜像。
- 行内**离线**（但实测 yum 源与内部 pip 源可达，见 5.5）。

### 5.2 改造范围全景

一次完整的国产化改造要覆盖四类镜像，工作量从大到小：

| # | 类别 | 说明 | 状态 |
|---|------|------|------|
| A | **自研镜像** | 后端 `kubeflow-dashboard`、前端 `kubeflow-dashboard-frontend` | 🔄 后端 py3.12 迁移中，已在行外3.12上验证；前端待安全部口径 |
| B | **中间件镜像** | minio / redis / istio / grafana / dcgm-exporter / volcano 等第三方服务 | 🔄 8 个已改造验证，redis 受阻 |
| C | **业务 Pod 镜像** | notebook、job-template 引用的 16 个镜像（81 处 `python:3.9` 注册） | ⏳ 待排期 |
| D | **K8s 平台组件** | kube-system / flannel / metallb | ❌ 不属于改造范围 |

### 5.3 需要改造的中间件清单 ★（目前程润铎老师在进行）

经盘点，K8s 集群里的中间件镜像**全部存在超危/高危组件**。调研结论很关键：

> **所有扫描出的超危/高危 CVE 都来自 base OS 层（Debian/Ubuntu/Alpine/UBI8 的系统包），业务二进制本身是干净的。**
> 所以改造路径统一为「**把业务二进制搬到麒麟基座**」，而不是去逐个修补系统包。

#### 5.3.1 逐镜像清单（9 个）

| # | 原镜像 | 用途 | 原 Base OS | 业务二进制 | 改造方式 | 状态 |
|---|--------|------|-----------|-----------|---------|------|
| 1 | `minio/minio:RELEASE.2023-04-20T17-56-55Z` | S3 对象存储（Pipeline 日志/产物） | UBI8-minimal | 静态 Go | 拷二进制 | ✅ 已验证 |
| 2 | `grafana/grafana:9.5.20` | 监控面板 | Alpine | 静态 Go | 拷文件树 | ✅ 已验证 |
| 3 | `istio/pilot:1.15.0` | 服务网格控制面（istiod） | Ubuntu 22.04 | 静态 Go | 拷二进制 | ✅ 已验证 |
| 4 | `istio/proxyv2:1.15.0` | Envoy sidecar / 入口网关 | Ubuntu 22.04 | envoy 动态 | 拷二进制 + **iptables rpm** | ✅ 已验证 |
| 5 | `nvidia/dcgm-exporter:3.1.7-3.1.4-ubuntu20.04` | GPU 指标导出 | Ubuntu 20.04 | 动态 + libdcgm | 拷二进制 + 厂商库 | ✅ 二进制级验证（集群无 GPU 节点） |

#### 5.3.2 为什么 redis 是唯一卡住的

redis-server 是动态链接的 C 程序，依赖 Debian 12 的 **glibc 2.36 + OpenSSL 3.x**；麒麟 V10 SP3 是 **glibc 2.28 + OpenSSL 1.1.1f**，跨度太大，二进制直接搬不过来：

```
libm.so.6:  version `GLIBC_2.29' not found
libc.so.6:  version `GLIBC_2.33' / `2.32' / `2.34' not found
libssl.so.3    => not found
libcrypto.so.3 => not found
```

**三条候选路线**（按推荐度）：

| 方案 | 做法 | 说明 |
|------|------|------|
| **A（首选）** | 行内麒麟源直接 `yum install redis` | 最干净，麒麟原生二进制。**前提：确认麒麟源有 redis 包** |
| B | 麒麟环境编译 redis 源码（7.4.3） | 产出原生二进制，需源码 tarball + openssl-devel |
| C（兜底） | 保留 Bitnami 目录结构，只替换 `redis-server`/`redis-cli` 二进制 | K8s 部署已覆盖 command，实际只需两个二进制在 PATH |

**不可取**：把 Debian 的 glibc 2.36 + libssl.so.3 一起打包搬进去 —— 等于把旧 CVE 原样搬过去，违背改造目标。

> 部署侧无变化：`command: [redis-server, /usr/local/etc/redis/redis.conf]`，探针 `redis-cli -a admin ping`，数据目录 `/data`（PVC），配置走 ConfigMap。

### 5.4 自研镜像（目前饶铮老师在进行）

#### 5.4.1 后端 `kubeflow-dashboard`

- 现行麒麟链（`kylin-20260730-v6`，py3.9 + Miniconda）已送评：**超危 8 CVE / 高危 45 CVE**。
- 归因三层：rpm 层（perl / libxml2 / glibc / libssh / pam / libcurl / libarchive / krb5）+ conda base 层（certifi）+ conda python39 应用层（FAB 4.3.7 / Jinja2 / Werkzeug / gunicorn / urllib3…）+ npm 层（node16 自带 npm）。
- **决策：旧链不整改，直接迁 py3.12**（见 5.5），旧链的高危项作为迁移期已知风险，迁移后自然消失。
- 行内 py3.12 基座已送评：**超危 0，高危仅 2 条**（py3.7 老环境的 pip 20.2.2 / setuptools 44.1.1，构建期工具）——基座干净。

#### 5.4.2 前端 `kubeflow-dashboard-frontend`

- 已是麒麟基座构建，但**扫描仍报错**：根因是 yum 装的 **nginx 及其依赖的 perl**（perl 5.28 有超危 9.8）。
- 两条路：
  - **最小化 nginx**（exclude 掉 perl 等非必需模块）—— 待安全部给"什么能过检测"的明确口径；
  - **换 Caddy** 方案已备好（`fix/fe-caddy-kylin.tgz`，Caddy 2.9.1）。
- 前端运行时**只需要一个静态 web 服务器**，node/npm 不进生产镜像（后端代码也无运行时 node 调用，已全库 grep 确认）。

- **只有 6 个 wheel 必须离线带入**：`gssapi`、`decorator`、`docopt`、`wtforms_json`、`jieba`、`hdfs`（源上只有 sdist 或 Requires-Python 不兼容）。
- `requests-kerberos==0.15.0` 与 `pyspnego==0.12.2` 需 `--no-deps` 安装（依赖声明会拉 gssapi 挂掉）。
- 行内 yum 实测可用；但**升级需 `--exclude` 防降级**（行内 updates 源版本滞后于基座，如 krb5-libs 会被 23→17 降级）。

### 5.6 目前的问题与待确认 ★

| # | 问题 | 影响 | 状态/建议 |
|---|------|------|----------|
| 1 | **redis 中间件无法直接搬麒麟基座** | Celery broker 跑不起来 | 待确认麒麟源是否有 redis 包（决定走方案 A/B） |
| 2 | 前端 nginx 的 perl 超危 | 前端镜像送评不过 | 待安全部给检测口径；Caddy 方案已备 |
| 4 | iptables 在容器内行为未验证 | istio-init 容器 | 需在测试集群跑 root + NET_ADMIN 冒烟 |
| 5 | 集群无 GPU 节点 | dcgm-exporter | 只能做二进制级验证，无法运行时冒烟 |
| 6 | job-template 16 个镜像 / 81 处 `python:3.9` 注册 | 业务 Pod 仍是老 Python | 待排期批量替换 |
| 7 | 迁移 deadline 未明确 | 决定灰度节奏与豁免策略 | 需向行内确认 |
| 8 | 评估平台是否支持构建期组件豁免/白名单 | 影响送评策略 | 需向行内确认 |

> 送评要点：系统层包应全部是 ky10 补丁版；业务二进制与原镜像 1:1（哈希可比对）；新增包需在报告中说明来源（当前 8 个中间件镜像**合计只新增 1 个 rpm**：`iptables-1.8.5-6.ky10`，仅 istio-proxyv2 用；非 rpm 新增仅 `/usr/bin/which` 两行 shell 脚本）。

## 7. 开发流程

### 7.1 日常改代码（增量构建，最快）

| 改了什么 | 命令 | 耗时 |
|----------|------|------|
| 仅后端 Python | `bash build_backend.sh [TAG]` | ~2 分钟 |
| 仅前端 React | `bash build_frontend.sh [TAG]` | ~3 分钟 |
| 前后端都改 | 先 `build_frontend.sh` 再 `build_backend.sh` | ~5 分钟 |

脚本自动：构建 → 推送 Harbor → `kubectl set image` → 等待 rollout。
后端镜像同时更新 4 个 Deployment（backend / schedule / worker / watch）。

### 7.2 本地调试

```bash
# 后端：docker-compose 起服务，或裸机跑
export FLASK_APP=myapp:app STAGE=dev
python myapp/run.py                      # 或 gunicorn myapp:app

# 前端（热更新）
cd myapp/frontend && npm install && npm run start   # localhost:3000，代理到后端
```

调试技巧：`@pysnooper.snoop()` 装饰器打印函数执行详情；`proxy.py` 是端口 8080 的请求日志代理。

### 7.3 依赖变更 / 数据库变更

- **新增 Python 依赖**：改了 `requirements.txt` 就要重建 base 镜像（需联网环境），再更新 `build_backend.sh` 里的 `BASE_IMAGE`。
  - 注意：`requirements.txt` 目前已是 **py3.12 版本**（FAB 5.2.2 / Flask 3.1.3），改之前先确认目标基座。
- **改了 Model**：`myapp db migrate -m "xxx"` 生成迁移脚本，容器启动时 `entrypoint.sh` 会自动 `db upgrade`。
- **覆盖任何文件前先备份**，备份统一放 `py312/backup/`（命名 `<原名>.<版本标记>.bak`）。

### 7.4 常用命令速查

```bash
kubectl get pods -A -o wide --sort-by='.spec.nodeName'   # 看所有 pod
kubectl logs -n infra deploy/kubeflow-dashboard --tail=50 -f  # 后端日志
kubectl exec -it -n infra deploy/kubeflow-dashboard -- bash   # 进容器
kubectl rollout restart deployment -n infra kubeflow-dashboard # 强制重建
```

## 8. 多人协作与代码合并

> 核心矛盾是：**创新实验室可直连 GitHub，行内测试环境不可联网**，且团队分散在上海、苏州两地。

### 8.1 代码托管与访问

- **唯一代码源 = 行内 Gitee**：http://git.cs.bosc:8000/bosc/bdas_bdm_group/bdas_bdm_cubestudio.git，所有人以此为准。
- 创新实验室直连 GitHub，用于对比上游改动；行内测试环境**不参与代码提交**，只做部署验证。
- 苏州同事通过 VPN/跳板机访问行内 Gitee 或创新实验室（具体入口待补）。

### 8.2 分支模型（推荐：简化 Git Flow）

```
main                 ── 稳定主干（只接受 merge，不直接 commit）
   └── final/dev     ── 开发主线（日常集成）
          ├── feature/<模块>   （例如 feature/hdfs-browser、feature/role-mgmt）
          └── fix/<问题>        （例如 fix/pipeline-timeout、fix/redis-kylin）
```

- 开发时从主开发分支拉 `feature/xxx`，完成后提 **PR** 合回。
- PR 需至少 1 人 Code Review 通过才可合并；`main` 的合并由集成负责人操作。

### 8.3 协作闭环

```
1. 认领任务（模块/页面，先在大群里声明，避免撞车）
2. git checkout -b feature/xxx
3. 本地开发 + 自测
4. push → 提 PR → Code Review → 合并到开发主线
5. 构建 → 创新实验室验证
6. 验证通过 → 打镜像 tar + copy_clean.sh → 离线交付到行内
7. 行内部署验证 → 有问题在 PR/issue 上反馈
```

### 8.4 提交与代码规范约定

- **提交前**：`git status` 确认没混入大文件/敏感文件（keytab、krb5.conf、kubeconfig、node_modules、tar 包）。
- **commit message** 建议用 `模块: 说明` 格式，例如 `feat(hdfs): 新增 Parquet schema 尾部读取`。
- **合并冲突**：以开发主线为准，冲突方在本地 `git rebase` 解决后再提 PR。
- **大文件/镜像产物**：一律不进 git，走离线交付流程（`copy_clean.sh` + `pull_pack_clean.sh`）。
