3配置体系：为什么 config.py 有四个副本 ★ 最容易踩坑

3.1 加载机制

镜像里 /home/myapp/myapp/config.py   ← 0 字节（空文件）
        ↑ 被 subPath 挂载「覆盖」
ConfigMap kubeflow-dashboard-config 的 config.py 键
        ↓
CONFIG_MODULE = os.environ.get("MYAPP_CONFIG", "myapp.config")
app.config.from_object("myapp.config")

MYAPP_CONFIG 在 K8s manifest 里从未设置 → 恒为默认值 myapp.config → 实际生效的就是「被 ConfigMap 覆盖后的 /home/myapp/myapp/config.py」。

同一个套路在本地 docker-compose 里也有一份（install/docker/docker-compose.yml:68）：

- ./config.py:/home/myapp/myapp/config.py
✅
结论：ConfigMap（生产）与 bind mount（开发）是同一种设计的两种投递方式。

3.3 ConfigMap 是怎么「被设计出来」的

install/kubernetes/cube/overlays/kustomization.yml：

configMapGenerator:
- name: kubeflow-dashboard-config
  files:
  - config/config.py
  - config/entrypoint.sh
  - config/project.py
  • 仓库里没有任何 kind: ConfigMap 的 yaml，它是 kustomize build 现生成的
  • configMapGenerator 默认给名字加内容哈希后缀（如 kubeflow-dashboard-config-kkg59f648t），并同步改写 deployment 里的引用 → 配置一变自动滚动更新
  • ⚠️ 该文件里注释掉的手动命令生成的名字不带哈希，和 deployment 引用对不上 —— 改了等于没改
💥
根因提示：config.py 是代码（含 import、类定义），不是 key=value 配置。 把它放进 ConfigMap，就注定「镜像内版本」与「ConfigMap 版本」要手动同步。
历史上那次 import imp CrashLoop 就是这么来的 —— py3.12 移除了 imp，镜像里改了、ConfigMap 里没改，启动即挂。
旁边那个 deploy-config 才是正确示范：纯 literals，永远不冲突。

11设计观察与风险点

#观察影响
1config.py 是代码不是配置，且存在 4 个互相不一致的副本镜像与 ConfigMap 版本漂移 → 历史 CrashLoop 根因。改配置必须两份一起改
2ConfigMap 名字带内容哈希后缀手动 kubectl create configmap 生成的名字对不上，改了不生效。必须走 kustomize build | kubectl apply -f -
3MyappModelRestApi 的 30 层 merge_response_func 装饰器加字段要同步改多个 merge_*，容易漏；但换来前端零硬编码表单
4home.py:menu() 约 650 行的巨型函数新增模块要动它；是导航中枢，改错全站菜单塌
5Model 层含大量 *_html 展示方法，且没有统一基类、没有 to_dict、没有软删除数据层不纯，元数据组装逻辑间接依赖，重构需谨慎
6K8s 类约 70 个方法集中于一个 2629 行文件是唯一集群交互出口（好处）；但单文件过大，拆分时须保留 make_pod 的单一注入点语义
7deploy-watch.yaml:140 凌晨 3 点主动自杀式探针有意为之的每日回收（watch 偶发挂死），排障时别误判为 OOM
8get_volume_mounts 是 @staticmethod，却依赖调用方传入 username 做卷展开传错 username 会挂到别人的卷上，是越权风险点
9myapp/project.py 同时承载 push_message 与 MyCustomRemoteUserView / Myauthdbview 登录视图职责混杂；且它也是被 ConfigMap 覆盖的第三个文件
10adjust_node_resource 在 per-cluster 循环里 return（schedules.py:1122/1130/1142/1152）只在第一个集群生效。虽然该任务当前未被调度（见 §7.1），但重启它前必须先修
11config_local.py:19-27 把 CELERY_CONFIG 换成没有 beat_schedule 的 dict本地 docker-compose 一个定时任务都不触发。排查"定时任务不生效"先看这里
12CeleryConfig.target_annotations 里的 task.exec_command（config.py:518-524）全仓无实现死配置项
13Pipeline 继承 ImportMixin 却没有 export_children=["task"]导出 pipeline 不会递归带上 task。ETL_Pipeline 的两行也被注释掉了
14表名与类名不一致：RunHistory→run、Training_Model→model、Sqllab_Query→sqlab_query（拼写就少一个 l）写原生 SQL / 查 migration 时容易踩
15models/__init__.py 为空，不做 re-export"某张表在哪个文件"只能靠文件名猜，IDE 跳转差
16前端 axios 实例没有 baseURL，api/index.tsx:5 那行 baseApi 是死代码；鉴权靠 myapp_username cookie换环境 / 加前缀时，代理人容易改错地方
17前端依赖 mobx 但没有实际全局 store看 store/ 目录会误以为有状态中心
