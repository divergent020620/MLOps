三个实现方案对比

核心目标：定时起Pod执行 → 完成释放资源，复用Job_Template模板体系，不依赖企业版算子

方案 A：新增 ScheduledJob 模型 + K8s CronJob

思路：新建一个 ScheduledJob 数据模型，用户选择模板 + 填 cron 表达式 + 填参数 → 后端生成 K8s CronJob 资源

新增模型：ScheduledJob (约10个字段)

新增视图：ScheduledJob_ModelView_Api

K8s 资源：CronJob（K8s 原生，无需 Argo）

代码改动：~300行（模型100 + 视图150 + K8s工具50）

前端：需要新建页面

优点

  • 最干净，独立模型不污染现有逻辑
  • K8s CronJob 原生支持，稳定可靠
  • 完全脱离企业版

缺点

  • 改动量大（新模型+新视图+新前端页面）
  • 需要前端开发新页面

方案 B：在现有 Service 模型上扩展 Cron 能力

思路：在现有的 Service 模型上加一个 schedule_type 字段。schedule_type='once' 就是现有的一次性服务，schedule_type='cron' 就生成 CronJob

模型改动：Service 模型加 2 个字段 (schedule_type, cron_expression)

代码改动：~150行（模型20 + 视图80 + K8s工具50）

前端：复用 Service 页面，加 cron 表单

优点

  • 改动小，复用现有 Service 的部署链路
  • 前端只需在现有页面加字段
  • 用户学习成本低

缺点

  • Service 和 CronJob 本质不同（常驻 vs 一次性），语义混淆
  • 后续维护时两种模式互相牵制

方案 C：复用 Pipeline 模型 + 旁路 K8s Job（非 Argo）

思路：继续用 Pipeline + Task 模型定义跑批逻辑，但在执行时绕过 Argo → 直接生成 K8s Job（非 CronJob），配合外部 Cron 调度

模型改动：几乎不变，Pipeline 加一个 engine 字段(argo | native)

代码改动：~200行（新增 native job 生成器 + 定时器调度）

前端：几乎不变

优点

  • 复用现有 DAG 编排和模板选择逻辑
  • 前端完全复用

缺点

  • Pipeline 模型很重(40+字段)，为简单跑批引入复杂度
  • DAG 逻辑对单任务跑批来说是多余的
  • Cron 调度仍需自己实现
A

推荐：方案 A — 新建 ScheduledJob

最干净，模型语义清晰，CronJob 是 K8s 原生资源成熟稳定。唯一代价是新前端页面，但改动隔离性好。
