批处理 → 服务化：当前 vs 目标

Cube Studio 现有两条完全独立的链路，现在要把批处理也服务化

当前：Pipeline 批处理链路

触发方式：手动点击 / Cron 定时

执行引擎：Argo Workflow DAG

运行形态：每个 Task 是一个 Job Pod
（启动 → 执行 → 完成 → 销毁）

扩缩容：❌ 不支持

外部调用：❌ 无 API 入口

适用场景：离线训练、ETL、定时任务

User → [Run] → dag_to_pipeline()
→ Argo Workflow CRD → K8s Pods
→ 跑完销毁 (TTL 3h)
目标：批处理服务化链路

触发方式：HTTP/gRPC 请求 / 消息队列

执行引擎：常驻服务 + 内部批处理引擎

运行形态：Deployment 常驻 Pod
（始终运行，等待请求触发批处理）

扩缩容：✅ HPA 自动伸缩

外部调用：✅ REST API / gRPC

适用场景：在线推理、实时数据处理

Client → HTTP Request → Service Pod
→ 内部执行批处理逻辑 → 返回结果
→ Pod 继续运行等待下一请求

架构层面的变化

维度 当前 Pipeline 方式 服务化方式
K8s 资源 Argo Workflow CRD Deployment + Service + HPA
生命周期 跑完即止 7×24 常驻
调用方式 平台内触发 HTTP API 外部调用
弹性 固定资源 HPA 按 QPS/CPU 自动伸缩
任务编排 DAG 依赖 (Argo) 代码内调用链 / 消息队列
